## 2. 产品目标和软件分层

产品接收 PC 的卡片命令或本地配置指令，选择目标通道，与接触式卡／NFC 等设备交互，再返回结果；同时管理 USB、Type-C 状态、指示灯及持久化参数。

```text
PC 工具或读卡器应用
        ↓ USB
USBX CDC 接收／CCID 类处理（不同阶段）
        ↓ 完整业务请求
私有协议解析、命令路由、APDU 业务
        ↓ 设备接口
ISO7816／NFC／Flash 参数等封装
        ↓
STM32 HAL、芯片外设、板级硬件

ThreadX 在各层之间提供任务、Mutex、事件、队列和内存管理。
```

**公司私有接口不等于所有底层代码从寄存器写起。** 例如 Flash 封装调用 ST HAL；公司增加的是参数约束、设备接口、协议逻辑与集成。称为内部设备库／软件平台比较准确；是否是可供多产品复用的完整 SDK，还要看接口、配置与发布方式。

模块边界应解释为：USB 层处理传输；协议层识别请求；设备层完成卡片收发；参数层管理保存与加载。模块不必各自创建一条线程，线程是执行单元，模块是职责与接口边界。

## 3. 启动与任务资源

设计说明记录的主线：

```text
复位与 C 运行环境准备
 → main：HAL、时钟、DMA、Cache、板级外设及前置状态初始化
 → tx_kernel_enter()
 → ThreadX 内核初始化
 → tx_application_define() 创建应用资源与线程
 → 启动调度，各线程运行到自己的等待点
```

“MCU 上电直接进入 main”是简化说法；复位向量和 C 启动初始化在 main 之前。创建为就绪的线程也不等于此时已经运行或阻塞；通常要启动调度、执行到等待接口后才进入相应等待状态。SysTick 的一次 tick 是否等于 1 ms，要核对实际配置。

### 3.1 线程划分（来自整机设计说明，待核对当前代码）

| 线程 | 文档优先级 | 职责与需要解释的等待方式 |
| --- | --- | --- |
| USBPD_CAD_Task | 1 | Type-C／电源相关处理；具体保护是否由硬件实现另查。 |
| DhProtocolDataExchange | 5 | 命令解析、路由、应答；等待新命令事件。 |
| NciI2CTest | 6 | NFC 巡检；拿不到共享 I2C 锁则跳过本次。 |
| CommunicationStatus | 7 | 状态指示；实际周期与阻塞位置待补。 |
| app_ux_device_thread_entry | 10 | 消费 USB 启停队列，管理外设状态。 |
| usbx_cdc_acm_read_thread_entry | 20 | CDC 字节接收、完整帧拼接和业务通知。 |

ThreadX 通常数值越小优先级越高。不能只说“读卡优先级高所以能及时运行”：还要看接收任务能否获得 CPU、共享总线被占多久、锁是否启用继承、外设事务是否完成。文档中的 `HalDelayMs()` 是否真正阻塞让出 CPU，也要看其实现，不能根据名称推断。

### 3.2 内存与同步对象

设计说明划分约 10 KB 业务池、15 KB USBX 池、5 KB USBPD 池。这是资源预算与分配边界，**不是“物理故障完全隔离”**；若无 MPU 等保护，越界写仍可能影响别的模块。

| 对象 | 作用 | 关键追问 |
| --- | --- | --- |
| I2C Mutex `SyncObject` | 串行化共享总线事务。 | 创建时是否 `TX_INHERIT`；所有使用者是否用同一把锁；异步传输何时释放。 |
| `EventFlag` | 接收方通知业务线程有完整请求。 | 位何时清；连续请求是否合并；缓冲区是否可能被覆盖。 |
| `ux_app_MsgQueue` | 传递 USB 启停请求。 | 元素格式、容量、满队列、重复启停与状态检查。 |
| `FlashSyncObj` | 运行时串行化 Flash 访问。 | 实际宏是否包装 Mutex、等待上限、错误路径释放。 |

事件标志只表示条件，不自动复制业务数据。`UserRxBufferFS`／`APDUBuffer` 等共享缓冲区需要明确生产者、消费者、容量和所有权；高优先级任务及时运行不能代替缓冲区协议。

## 4. 从主机到卡片再回主机的调用链

整机说明记录的 CDC 阶段流程：

```text
主机封装请求 → USB CDC 收字节 → 拼接完整帧
 → 置位接收事件 → 读卡线程取得并解析命令
 → 检查通道 → 区分本地私有指令与卡片命令
 → APDU 路由 → 获取设备资源 → 硬件交互
 → 生成状态／应答 → 封装回传 → 主机解析及日志
```

相关接口包括 `DhProtocolGetCommand()`、`DhProtocolApduDispatch()`、`DhProtocolProprietary()`、`Iso7816TransceiveApdu()`、`DhProtocolSendResponse()` 和 `HalIoDhWrite()`。这些是调用链线索，接口内部是否调用 HAL、专用芯片或其他库，需读源码确认。

### 4.1 协议背景和面试边界

- **ISO7816：** 接触式智能卡相关接口与协议；T=0、T=1 是不同传输协议，不能直接当作两种 APDU 格式。
- **APDU：** 上层命令／响应单元。命令是否含 Lc、Le 取决于情况，不能认为每条都固定含全部字段；通常响应数据后有 SW1/SW2。
- **PPS：** 卡通信参数协商。主机通过公司私有配置命令修改 PPS 策略，与在卡链路上真正执行 PPS 是两个阶段。
- **私有外壳：** 原 CDC 业务帧负责通道、长度、完整性等，里面承载 APDU；CRC 通过不等于业务执行成功。
- **接收边界：** 一次 USB 接收回调不一定是一条完整业务帧，需按协议长度做限幅、组包和异常恢复。

### 4.2 I2C 策略为什么这样选？

读卡路径允许等待资源，是为了完成当前请求；巡检属于可延后的后台工作，非阻塞失败后跳过，避免无意义排队。但 `TX_WAIT_FOREVER` 不是“保证优先”，也不是实时期限；若持锁者不释放，读卡也会一直等。需要核对锁的继承配置、最大持锁时间、驱动超时及失败后的恢复。

## 5. PPS 参数与 Flash 持久化

### 5.1 材料记录的设计

Flash 说明记录：启动时由 `DhVarInit()` 加载参数；旧方案由后台线程检查全局请求标志并异步写入，新方案将保存同步放入私有指令处理链。参数涉及 PPS 开关及波特率档位；运行时用同步对象保护访问。

```text
配置请求 → 长度／参数范围检查 → 组织新参数
 → 取得 Flash 锁 → 读取旧内容 → 修改目标字段
 → 擦除 → 按 QuadWord 编程 → 释放锁 → 返回结果
```

同步方案便于定义“应答成功时是否已经保存”，减少后台状态和任务栈开销，但会延长业务线程占用和请求响应时间。异步方案可较早返回，但必须说明应答表示“已接收”还是“已持久化”，并保存请求内容、完成状态和失败结果。不能简单说某一种必然更实时。

### 5.2 接口和 C 语言细节

- `Flash_Word_Read(addr, &value)` 通过输出指针回填读取结果；这不是申请堆内存。
- `Flash_Page_Erase()` 包装解锁、擦除配置、HAL 调用及错误检查；实际擦除单位要以 H563 手册为准，不能只看函数名“Page”。
- `Flash_Word_Write()` 将一个 32 位业务参数装入 16 字节缓冲区，再调用 QuadWord 编程。**业务参数大小与硬件编程粒度不同。**
- 文档中的 `static ... quad_buf[4]` 具有静态存储期，不依赖函数栈帧；它在调用间共享，所有并发访问要按同一同步规则保护。
- `volatile` 地址读取限制编译器优化，不等于关闭硬件 Cache。缓存维护和编程后可见性应按实际芯片配置处理。

### 5.3 文档片段中需要继续核实的风险

这些是从整理说明发现的问题，不直接认定当前固件仍然存在，更不能说自己已经修复：

| 风险 | 为什么要追问 | 合理的改进方向，未确认已实现 |
| --- | --- | --- |
| 上层未逐步检查读／擦／写返回值，仍可能应答成功。 | 底层失败如何通知主机？ | 统一错误传播，失败不返回成功。 |
| 先更新 RAM，再持久化。 | 写失败时当前生效值和下次上电值是否不同？ | 明确定义生效／提交策略及回滚或脏状态。 |
| 把空白 Flash 当成读取失败。 | 读取擦除态内容可能成功，但内容全为 1。 | 检查有效标记、范围、版本及需要的校验。 |
| 读一个字后擦整页。 | 同页其他有效数据是否被误删？ | 确认是专用页，或设计完整页保存策略。 |
| 每次配置都擦写同一位置。 | 擦写寿命和重复值写入如何处理？ | 减少无效写入，必要时做轮转。 |
| 擦除后写入前掉电。 | 有效旧参数是否已经丢失？ | 双记录／双区、序号、有效性校验和提交标记等方案。 |

“断电后正常重启能读回”与“任意写入时刻掉电均能恢复”是两种不同承诺。启动阶段无需锁的理由是确认不存在并发访问，不是“读操作天然不需要同步”；已有说明中的启动与运行时并发描述也需核对时序。

## 6. CDC 到 USBX-CCID 迁移

这是简历中独立的一条工作线，不能把 CDC 工程说明直接当成最终 CCID 架构。

- CDC 提供虚拟串口通道，业务通常自行定义帧协议与组包。
- CCID 提供智能卡设备类命令与响应，主机请求进入设备类处理后再映射业务。
- 简历列出 `XfrBlock` 处理卡片传输、`Escape` 承载相应私有扩展；具体支持、权限、输入输出和缓冲区归属待核实。
- 迁移要检查设备描述符、端点、主机驱动、类回调、请求长度、卡槽状态和业务应答，不能只替换两个函数名。

### 6.1 “64 字节 Bulk 接收阻塞”怎样准备？

当前只能确认简历提出过这个问题，缺少故障日志与最终改动，**不能预先认定是少发 ZLP，也不能认定是 USBX 的 Bug**。

1. 先确认 USB 速度、端点最大包长，以及 64 指的是 USB 包、类消息、缓冲区还是实际业务长度。
2. 同时记录主机请求长度、设备请求接收长度和 actual length；区分 USB packet、一次 transfer 与完整 CCID 消息。
3. 在临界长度前后、以及最大包长整数倍附近对照，确认停在 USB 层、类层回调还是业务等待。
4. 核对协议声明长度、组包状态、缓冲区容量、超时与应答；是否需要短包／ZLP，要结合具体传输方向和结束条件判断。
5. 最终补“原始现象 → 日志证据 → 根因 → 修改 → 边界回归”，再写成亲历案例。
