## 2. 产品目标和软件分层

产品接收 PC 的卡片命令或本地配置指令，选择目标通道，与接触式卡／NFC 等设备交互，再返回结果；同时管理 USB、Type-C 状态、指示灯及持久化参数。

```text
PC 工具或读卡器应用
        ↓ USB
USBX CDC 接收／CCID 类处理（不同阶段）
        ↓ 完整业务请求
私有协议解析、命令路由、APDU 业务
        ↓ 设备接口
ISO7816／NFC／Flash 参数等封装
        ↓
STM32 HAL、芯片外设、板级硬件

ThreadX 在各层之间提供任务、Mutex、事件、队列和内存管理。
```

**公司私有接口不等于所有底层代码从寄存器写起。** 例如 Flash 封装调用 ST HAL；公司增加的是参数约束、设备接口、协议逻辑与集成。称为内部设备库／软件平台比较准确；是否是可供多产品复用的完整 SDK，还要看接口、配置与发布方式。

模块边界应解释为：USB 层处理传输；协议层识别请求；设备层完成卡片收发；参数层管理保存与加载。模块不必各自创建一条线程，线程是执行单元，模块是职责与接口边界。

### 2.1 主控选型：STM32H563ZI 为什么适合读卡器？

选型要从“产品需要什么”解释到“芯片提供什么”，不能只罗列主频和接口。这里根据本人确认的型号、已有设计说明和官方资料做适配分析，**不代表本人是最初选型决策者，也不代表所有硬件能力已经在项目中启用。**

这款读卡器需要处理 PC 的 USB 请求、协议解析、卡片／NFC 访问、Type-C 状态、参数持久化和多线程协作。H563ZI 的主要匹配点如下：

| 选型维度 | 官方参数／能力 | 对本产品的价值 |
| --- | --- | --- |
| CPU | 单核 32 位 Arm Cortex-M33，最高 250 MHz，带 FPU、MPU、TrustZone。 | 为协议处理、驱动、中断后处理和 RTOS 调度留出算力余量；不是多个线程同时在多个 CPU 核上执行。 |
| 程序存储 | ZI 的 Flash 容量为 2 MB；支持双 Bank 与跨 Bank 的读写并行能力。 | 容纳业务固件、HAL、ThreadX、USBX 等代码，并给后续扩展留空间；实际空间分配由链接与固件布局决定。 |
| 运行内存 | 主 SRAM 共 640 KB，另有 4 KB 备份 SRAM。 | 容纳任务栈、内核对象、通信缓冲及内存池，降低资源紧张程度；不是 640 KB 都能直接交给应用。 |
| 封装与连接 | Z 对应 144 引脚规格，LQFP144 封装。 | 多接口与控制信号有更多布线选择；引脚总数包含供电、地、复位等，不能说成 144 个可自由使用的 GPIO。 |
| 通信外设 | I2C、SPI、UART／USART、USB FS、UCPD 等。 | 覆盖 PC 连接、外部器件、调试及 Type-C／PD 管理所需接口；需进一步核对实际使用实例及复用冲突。 |
| 可靠性与隔离基础 | 部分 SRAM 的 ECC、MPU、TrustZone、看门狗等。 | 可作为错误检测、访问保护和故障恢复设计的基础；具有硬件能力不等于软件已经配置保护。 |

核心资料：[ST 产品页](https://www.st.com/en/microcontrollers-microprocessors/stm32h563zi.html)、[DS14258 Rev 6 数据手册](https://www.st.com/resource/en/datasheet/stm32h563zi.pdf)，重点看封面参数、表 2、§3.4–3.5、§3.42–3.43 和订货信息。下文是针对产品的工程分析，不是实测性能报告。

### 2.2 外设与引脚：丰富在哪里，怎样对应产品？

H563 器件提供最多 4 路 I2C、6 路 SPI、12 路 U(S)ART 加 1 路 LPUART；不同封装的引出情况要看表 2 和复用表。**外设实例数量、封装引脚数量、能够同时使用的接口数量是三件事。** 不能把每个接口都按最大数量同时接出来。

| 接口／资源 | 结合读卡器怎样解释 | 需要保留的边界 |
| --- | --- | --- |
| I2C | 设计说明已有 NFC 巡检和读卡路径共享 I2C 的描述，可承载相关器件访问。 | 足够多的 I2C 实例可以支持分总线设计，但已有工程是否这样做、为何共享，需看原理图。 |
| SPI | 可以连接采用 SPI 的外部器件或扩展存储。 | 这是选型可扩展性，不应凭芯片支持就宣称读卡器已通过 SPI 连接某器件。 |
| UART／USART | 可用于串口调试、外设通信；部分 USART 具备 ISO7816 智能卡模式。 | 仍需外部电气接口／供电等配合；当前卡接口究竟通过 MCU USART 还是专用芯片，待看原理图和调用实现。 |
| USB 2.0 Full-Speed | 芯片原生支持 USB 主机／设备，适合本项目以设备身份运行 CDC 或 CCID。 | FS 的线路速率是 12 Mbit/s，实际业务吞吐还要扣除协议开销；“USB 2.0”不等于 480 Mbit/s High-Speed。 |
| UCPD | 原生 Type-C／USB PD 控制器处理 CC 检测、PD 消息收发等，适配项目 Type-C／USBPD 管理。 | Type-C 是连接器体系；UCPD 管 CC／PD，USB 控制器管 USB 数据。还需要策略软件、供电通路及必要的保护电路。 |
| DMA | 支持相应外设与内存之间的数据搬运，可减少 CPU 按字节搬数据的负担。 | 需要实际配置和驱动配合；DMA 不是额外一个应用 CPU，也不自动解决缓冲区并发问题。 |

可以这样说：“接口丰富的价值，是在满足 USB、Type-C 和卡片外围连接的同时，还能留出调试及扩展资源。”真正确认够用要列出原理图信号表，检查复用冲突、供电电平、外设时钟和调试引脚，而不是只数管脚。

USB FS 速率依据：[ST USB 硬件与 PCB 指南 AN4879](https://www.st.com/resource/en/application_note/an4879-introduction-to-usb-hardware-and-pcb-guidelines-using-stm32-mcus-stmicroelectronics.pdf)。UCPD 的具体能力见数据手册 §3.43；本笔记不推定项目已经支持某个 PD 功率档位。

### 2.3 640 KB SRAM 与 2 MB Flash 分别解决什么问题？

**Flash 像“程序仓库”，SRAM 像“运行时工作台”。** Flash 保存固件和安排在其中的非易失数据；SRAM 放任务栈、变量、临时缓冲和 RTOS 对象。增加 SRAM 不会自动增加 CPU 核数，也不会让程序自动变成多线程。

主 SRAM 的组成是 `256 KB SRAM1 + 64 KB SRAM2 + 320 KB SRAM3 = 640 KB`，另有 4 KB 备份 SRAM。数据手册明确：SRAM3 若启用 ECC，其中 64 KB 要用于校验存储，因此主 SRAM 的可用数据容量会相应减少；还要考虑安全域、链接布局及其他保留用途。

**为什么多线程系统更需要运行内存？** A 线程等待卡片时，其调用链、局部变量和上下文仍要保存；切到 B 线程处理 USB 时，B 也需要自己的栈和缓冲区。各线程不必同时执行，却需要同时保留各自的运行状态。

```text
运行内存预算
 = 全局／静态数据
 + 各线程栈与必要的中断／系统栈
 + 内核控制块、队列、事件、互斥锁等对象
 + USB／协议／卡片收发缓冲
 + 尚未包含在上述项目中的堆或内存池空间
 + 对齐、硬件配置限制和安全余量
```

例如假设 6 条线程各分配 2 KB 栈，仅线程栈就是 12 KB。**这只是教学假设，实际工程栈大小未核验。** 本项目说明中的约 10 KB 业务池、15 KB USBX 池、5 KB USBPD 池也不是整机全部 SRAM 消耗；如果线程栈或缓冲从池中分配，预算时不能再重复相加。

因此合适的表达是“640 KB SRAM 能给 ThreadX 多线程和 USBX 缓冲提供较充裕的资源预算”，不应说“必须有 640 KB 才能跑多个线程”。F103 等小容量 MCU 也能运行 RTOS，只是栈、缓冲和组件选择要更克制。

2 MB Flash 的价值是固件体积余量。双 Bank 能为升级和运行时写入提供设计选择，但**不自动等于已实现双镜像 OTA、不停机擦写或掉电安全**；还取决于代码和向量表位置、访问哪个 Bank、分区以及提交策略。参数保存仍需考虑擦写粒度、寿命和断电窗口。

要回答“内存真的够吗”，最终应拿链接 map 文件、各线程栈高水位、内存池分配失败记录、峰值缓冲需求和功能同时运行的测试结果说明；不能仅用标称容量下结论。

### 2.4 250 MHz 对这款读卡器有什么具体价值？

250 MHz 表示每秒 2.5 亿个核心时钟周期，一个周期约 4 ns。**一个周期不等于执行完一条 C 语句，也不保证每条机器指令都只需一个周期。** 实际时间还受指令、访存、Flash 等待、Cache 命中和总线竞争影响；250 MHz 也是芯片上限，工程实际频率要看 `SystemClock_Config()`、RCC 配置及 `SystemCoreClock`。

读卡器的典型路径是“USB 接收 → 帧／长度校验 → 命令与 APDU 路由 → 卡片访问 → 组包应答”，期间还要处理 Type-C 状态、NFC 巡检、超时和线程切换。较高算力的具体意义是：

1. **更快完成 CPU 计算部分。** 如协议解析、数据复制、状态机执行，以及由软件实现时的校验计算；能较早提交外设请求或发出应答。
2. **给多种工作同时到来留出处理余量。** USB 收到请求时，可能还发生外设完成中断和 Type-C 事件；短小的处理工作更容易在各自时间预算内完成。
3. **降低相同计算负载所占的 CPU 比例。** 为新增日志、诊断和更完整的错误处理留空间，但增加功能后仍要重新评估最坏延迟。

一个纯计算的示意：假设某处理段在两个平台上都恰好花费 100,000 个核心周期，250 MHz 下约为 `100000 / 250000000 = 0.4 ms`，72 MHz 下约为 `1.39 ms`。这只解释“频率与时间”的关系，**不是 H563 对 F103 的实测倍速**，跨架构的周期数通常也不同。

例如 CPU 已用 0.4 ms 解析完请求，但卡片还要 10 ms 才应答，继续提高主频不能直接消除卡片等待。类似地，USB FS 不会因 CPU 达到 250 MHz 就变成 USB HS；I2C／SPI 速度也由外设配置、器件和电气条件决定。

H563 还有 8 KB 指令 Cache、用于外部存储的 4 KB 数据 Cache 及 DMA 等配套资源。不能只比较 MHz，也不能把这里的 DCACHE 理解成所有内部 SRAM 都像 Cortex-M7 一样需要同一种缓存维护。FPU 对实际浮点运算有帮助，但不能将它包装成 APDU 收发的核心性能来源。

**高主频不保证实时性。** 优先级不合理、长临界区、锁长期占用、无超时等待仍会造成超时。正确选型流程是给端到端响应建立预算，测 CPU 占用和最坏延迟；功耗／温升也要随频率和工作模式一起考虑。

### 2.6 面试回答与选型取舍

> 这款产品使用 STM32H563ZI。我不是最初选型的决策者，但结合维护时接触的软件架构和数据手册，我理解它主要满足了三方面需求：第一，144 引脚封装及 USB FS、UCPD、I2C、SPI 等外设，给 PC 通信、Type-C 管理和卡片外围连接提供资源；第二，640 KB SRAM 和 2 MB Flash，便于容纳 ThreadX、USBX、任务栈和通信缓冲；第三，Cortex-M33 最高 250 MHz，为协议解析、并发事件处理和后续扩展提供算力余量。实际工程用了哪些接口、运行在多少 MHz，还应以原理图和时钟配置为准。它的价值是资源与需求匹配，最终还要结合内存占用、响应时间、功耗、成本和供应情况验证。

若面试官问“用 F103 不行吗”：不能只答“不够快”。应先核对确切 F103 型号，并比较引脚、USB／PD 支持、固件体积、栈与缓冲需求、最坏响应时间，以及是否需外加器件；再判断替代方案是否可行。现有资料不足以证明某个低配方案一定无法满足产品需求。

HAL、ThreadX、USBX 和公司既有封装的复用，有利于降低集成与维护工作量；但这属于软件平台适配价值，不能说成 H563 独占的功能。成本、功耗、封装面积和供货同样是取舍项，目前没有本项目的报价或测量数据，不给出虚构的量化收益。

## 3. 启动与任务资源

设计说明记录的主线：

```text
复位与 C 运行环境准备
 → main：HAL、时钟、DMA、Cache、板级外设及前置状态初始化
 → tx_kernel_enter()
 → ThreadX 内核初始化
 → tx_application_define() 创建应用资源与线程
 → 启动调度，各线程运行到自己的等待点
```

“MCU 上电直接进入 main”是简化说法；复位向量和 C 启动初始化在 main 之前。创建为就绪的线程也不等于此时已经运行或阻塞；通常要启动调度、执行到等待接口后才进入相应等待状态。SysTick 的一次 tick 是否等于 1 ms，要核对实际配置。

<a id="thread-layout"></a>

### 3.1 线程划分（来自整机设计说明，待核对当前代码）

| 线程 | 文档优先级 | 职责与需要解释的等待方式 |
| --- | --- | --- |
| USBPD_CAD_Task | 1 | Type-C／电源相关处理；具体保护是否由硬件实现另查。 |
| DhProtocolDataExchange | 5 | 命令解析、路由、应答；等待新命令事件。 |
| NciI2CTest | 6 | NFC 巡检；拿不到共享 I2C 锁则跳过本次。 |
| CommunicationStatus | 7 | 状态指示；实际周期与阻塞位置待补。 |
| app_ux_device_thread_entry | 10 | 消费 USB 启停队列，管理外设状态。 |
| usbx_cdc_acm_read_thread_entry | 20 | CDC 字节接收、完整帧拼接和业务通知。 |

ThreadX 通常数值越小优先级越高。不能只说“读卡优先级高所以能及时运行”：还要看接收任务能否获得 CPU、共享总线被占多久、锁是否启用继承、外设事务是否完成。文档中的 `HalDelayMs()` 是否真正阻塞让出 CPU，也要看其实现，不能根据名称推断。

<a id="memory-and-sync"></a>

### 3.2 内存与同步对象

设计说明划分约 10 KB 业务池、15 KB USBX 池、5 KB USBPD 池。这是资源预算与分配边界，**不是“物理故障完全隔离”**；若无 MPU 等保护，越界写仍可能影响别的模块。

| 对象 | 作用 | 关键追问 |
| --- | --- | --- |
| I2C Mutex `SyncObject` | 串行化共享总线事务。 | 创建时是否 `TX_INHERIT`；所有使用者是否用同一把锁；异步传输何时释放。 |
| `EventFlag` | 接收方通知业务线程有完整请求。 | 位何时清；连续请求是否合并；缓冲区是否可能被覆盖。 |
| `ux_app_MsgQueue` | 传递 USB 启停请求。 | 元素格式、容量、满队列、重复启停与状态检查。 |
| `FlashSyncObj` | 运行时串行化 Flash 访问。 | 实际宏是否包装 Mutex、等待上限、错误路径释放。 |

事件标志只表示条件，不自动复制业务数据。`UserRxBufferFS`／`APDUBuffer` 等共享缓冲区需要明确生产者、消费者、容量和所有权；高优先级任务及时运行不能代替缓冲区协议。

#### 3.2.1 已明确理解的互斥锁场景

本人已能明确说明的场景是：读卡主线程与 NFC 巡检线程可能同时访问共用 I2C，总线事务通过同一把互斥锁串行化。读卡路径允许阻塞等待；巡检尝试非阻塞获取，失败跳过本次。仍需关注实际超时、最大持锁时间和继承配置，不能把无限等待等同于保证实时性。

Flash 读写也有同步对象的文档线索，具体实现及后续优化前后的变化待核对。**把后台异步保存改成同步保存，不等于互斥锁一定可以取消。** 是否需要锁取决于还有没有其他并发访问者；若已改为唯一线程负责访问，也应先确认启动、运行时和其他回调路径，不凭“同步写”三个字判断。

<a id="event-flags-usage"></a>

#### 3.2.2 事件标志：USB 完整收包后通知读卡线程

**依据与边界：** 本人尚未找到明确的当前源码；《RCREADER_整机软件设计说明》第 4 页记录 `EventFlag` 的用途，第 7 页 §5.2 记录 `tx_event_flags_set()` 与 `RX_NEW_RECEIVED`。这些是已有文档线索，不是临时设想，也不代表已核实当前固件或最终 CCID 阶段仍使用同一实现。

USB 接收和读卡业务属于不同线程。PC 的一条请求可能分多次接收，接收线程应先拼成完整请求，再通知业务线程处理；不能收到任意一段字节就当作完整 APDU。

```text
USB 接收线程                              读卡主线程
usbx_cdc_acm_read_thread_entry             DhProtocolDataExchange
        │                                        │
分次接收、组包                            等待“收到新命令”的事件
保存完整请求到接收缓冲                    等待期间不占 CPU 空转
        │                                        │
置位 RX_NEW_RECEIVED ───────────────────→ 等待条件满足，进入就绪态
                                                 │
                                         获得 CPU 后解析请求
                                         访问卡片、组织应答
                                         再次等待新命令
```

| 要素 | 文档线索／需要核对的实现 |
| --- | --- |
| 通知方 | `usbx_cdc_acm_read_thread_entry`。 |
| 接收缓冲 | `UserRxBufferFS`；进入协议处理后还涉及 `APDUBuffer` 等缓冲。 |
| 事件对象与事件位 | `EventFlag`、`RX_NEW_RECEIVED`。 |
| 设置事件 | 说明明确提到 `tx_event_flags_set()`。 |
| 等待事件 | 搜索读卡线程中的 `tx_event_flags_get()` 或相应封装，确认等待条件、超时与清位方式；目前未核对具体调用。 |

可以把事件理解为门铃：“数据已经准备好了，可以来处理。”**事件携带的是条件，APDU 数据仍保存在缓冲区里。** 满足条件后线程恢复就绪，不等于已经运行或处理完；具体执行时机仍受调度约束。

面试追问通常是：读卡线程还没消费完，USB 又接到下一条命令怎么办？需要核对是否限制一次只有一条未完成请求，或已有缓冲交接、双缓冲、数据队列等机制，不能假定项目已实现。相同事件位在未被消费期间反复置位不能当作请求计数；事件清位也不等于接收缓冲已经可以覆盖。

<a id="usb-command-queue"></a>

#### 3.2.3 消息队列：PD 线程向 USB 管理线程发送启停指令

**依据与边界：** 《整机软件设计说明》第 4 页记录 `ux_app_MsgQueue` 和 USB 管理线程的职责，第 6 页 §3.1 记录 `START_USB_DEVICE`、`STOP_USB_DEVICE`。实际消息格式、发送／接收函数、容量和异常处理尚未核对源码。

```text
Type-C／PD 管理线程
        │
        │ 产生启动或停止 USB 的请求
        ▼
ux_app_MsgQueue 消息队列
        │
        ▼
app_ux_device_thread_entry
        │
        ├─ START_USB_DEVICE → 检查状态，执行 USB 启动流程
        └─ STOP_USB_DEVICE  → 检查状态，执行 USB 停止流程
```

文档举的业务场景是：空闲超时后，PD 线程发送停止 USB 请求；重新插拔 Type-C 后发送启动请求。具体超时、唤醒条件，以及停止 USB 后整机是否进入某种低功耗模式，要核对实际状态机，不能只凭指令名称推定。

队列中的消息相当于工作单：“请执行停止 USB 这个操作。”PD 线程提出请求，USB 管理线程集中执行启停，便于串行管理 USB 外设状态，避免多个模块直接交叉调用启停接口。**发送成功表示消息已交付给接收方或队列，不代表 USB 操作已经完成；若调用方需要完成结果，还要有明确的回报机制。**

源码可搜索 `ux_app_MsgQueue`、`START_USB_DEVICE`、`STOP_USB_DEVICE`、`tx_queue_send()`、`tx_queue_receive()` 及公司封装。重点核对消息元素大小、队列容量、满队列策略、错误返回、重复请求，以及拔线／重连时的状态处理。

普通 FIFO 入队方式可以保存多条请求的顺序；如果改用事件位同时表示 START 和 STOP，单凭两个位不能还原先后顺序。但队列也不会自动保证状态正确，消费者仍需检查设备当前状态和正在执行的事务。普通队列复制的是配置大小的消息内容；若元素包含指针，只复制指针，所指对象仍需管理生命周期。

#### 3.2.4 三种机制在本项目中的区别

| 机制 | 读卡器场景 | 主要回答的问题 |
| --- | --- | --- |
| 互斥锁 | 读卡主线程和 NFC 巡检共享 I2C；Flash 并发访问另查。 | 谁现在能使用这项共享资源？ |
| 事件标志 | USB 完整收包后通知读卡线程。 | 某个处理条件是否已经满足？ |
| 消息队列 | PD 线程向 USB 管理线程发送启停指令。 | 接下来具体执行什么操作，待处理请求如何暂存？ |

目前合适的经历表达是：“我能结合 I2C 说明互斥锁的实际用途；设计说明中，事件标志用于 USB 收包通知，消息队列用于 USB 启停请求。我会继续核对相应发送端、等待／接收端和缓冲管理代码。”不能把文档阅读说成独立实现这些机制。

机制参考：[ThreadX 事件设置实现](https://github.com/eclipse-threadx/threadx/blob/master/common/src/tx_event_flags_set.c)、[ThreadX 队列发送实现](https://github.com/eclipse-threadx/threadx/blob/master/common/src/tx_queue_send.c)。项目行为以实际版本、配置及调用参数为准。

<a id="request-flow"></a>

## 4. 从主机到卡片再回主机的调用链

整机说明记录的 CDC 阶段流程：

```text
主机封装请求 → USB CDC 收字节 → 拼接完整帧
 → 置位接收事件 → 读卡线程取得并解析命令
 → 检查通道 → 区分本地私有指令与卡片命令
 → APDU 路由 → 获取设备资源 → 硬件交互
 → 生成状态／应答 → 封装回传 → 主机解析及日志
```

相关接口包括 `DhProtocolGetCommand()`、`DhProtocolApduDispatch()`、`DhProtocolProprietary()`、`Iso7816TransceiveApdu()`、`DhProtocolSendResponse()` 和 `HalIoDhWrite()`。这些是调用链线索，接口内部是否调用 HAL、专用芯片或其他库，需读源码确认。

<a id="protocol-background"></a>

### 4.1 协议背景和面试边界

- **ISO7816：** 接触式智能卡相关接口与协议；T=0、T=1 是不同传输协议，不能直接当作两种 APDU 格式。
- **APDU：** 上层命令／响应单元。命令是否含 Lc、Le 取决于情况，不能认为每条都固定含全部字段；通常响应数据后有 SW1/SW2。
- **PPS：** 卡通信参数协商。主机通过公司私有配置命令修改 PPS 策略，与在卡链路上真正执行 PPS 是两个阶段。
- **私有外壳：** 原 CDC 业务帧负责通道、长度、完整性等，里面承载 APDU；CRC 通过不等于业务执行成功。
- **接收边界：** 一次 USB 接收回调不一定是一条完整业务帧，需按协议长度做限幅、组包和异常恢复。

<a id="i2c-policy"></a>

### 4.2 I2C 策略为什么这样选？

读卡路径允许等待资源，是为了完成当前请求；巡检属于可延后的后台工作，非阻塞失败后跳过，避免无意义排队。但 `TX_WAIT_FOREVER` 不是“保证优先”，也不是实时期限；若持锁者不释放，读卡也会一直等。需要核对锁的继承配置、最大持锁时间、驱动超时及失败后的恢复。

<a id="pps-persistence"></a>

## 5. PPS 参数与 Flash 持久化

<a id="pps-design"></a>

### 5.1 材料记录的设计

Flash 说明记录：启动时由 `DhVarInit()` 加载参数；旧方案由后台线程检查全局请求标志并异步写入，新方案将保存同步放入私有指令处理链。参数涉及 PPS 开关及波特率档位；运行时用同步对象保护访问。

下列流程对应说明中的标准 QuadWord 编程版本；本轮本人另补充了 Bank2 EDATA 参数布局，两者是否对应不同版本或配置，见 [5.6](#edata-programming-check)，目前不合并成一套已核实实现。

```text
配置请求 → 长度／参数范围检查 → 组织新参数
 → 取得 Flash 锁 → 读取旧内容 → 修改目标字段
 → 擦除 → 按 QuadWord 编程 → 释放锁 → 返回结果
```

同步方案便于定义“应答成功时是否已经保存”，减少后台状态和任务栈开销，但会延长业务线程占用和请求响应时间。异步方案可较早返回，但必须说明应答表示“已接收”还是“已持久化”，并保存请求内容、完成状态和失败结果。不能简单说某一种必然更实时。

<a id="flash-c-details"></a>

### 5.2 接口和 C 语言细节

- `Flash_Word_Read(addr, &value)` 通过输出指针回填读取结果；这不是申请堆内存。
- `Flash_Page_Erase()` 包装解锁、擦除配置、HAL 调用及错误检查；实际擦除单位要以 H563 手册为准，不能只看函数名“Page”。
- 旧说明中的 `Flash_Word_Write()` 将一个 32 位业务参数装入 16 字节缓冲区，再调用 QuadWord 编程。**业务参数大小与硬件编程粒度不同；此处不能直接作为 EDATA 的编程方式。**
- 文档中的 `static ... quad_buf[4]` 具有静态存储期，不依赖函数栈帧；它在调用间共享，所有并发访问要按同一同步规则保护。
- `volatile` 地址读取限制编译器优化，不等于关闭硬件 Cache。缓存维护和编程后可见性应按实际芯片配置处理。

<a id="flash-risks"></a>

### 5.3 文档片段中需要继续核实的风险

这些是从整理说明发现的问题，不直接认定当前固件仍然存在，更不能说自己已经修复：

| 风险 | 为什么要追问 | 合理的改进方向，未确认已实现 |
| --- | --- | --- |
| 上层未逐步检查读／擦／写返回值，仍可能应答成功。 | 底层失败如何通知主机？ | 统一错误传播，失败不返回成功。 |
| 先更新 RAM，再持久化。 | 写失败时当前生效值和下次上电值是否不同？ | 明确定义生效／提交策略及回滚或脏状态。 |
| 把空白 Flash 当成读取失败。 | 读取擦除态内容可能成功，但内容全为 1。 | 检查有效标记、范围、版本及需要的校验。 |
| 读一个字后擦整页。 | 同页其他有效数据是否被误删？ | 确认是专用页，或设计完整页保存策略。 |
| 每次配置都擦写同一位置。 | 擦写寿命和重复值写入如何处理？ | 减少无效写入，必要时做轮转。 |
| 擦除后写入前掉电。 | 有效旧参数是否已经丢失？ | 双记录／双区、序号、有效性校验和提交标记等方案。 |

“断电后正常重启能读回”与“任意写入时刻掉电均能恢复”是两种不同承诺。启动阶段无需锁的理由是确认不存在并发访问，不是“读操作天然不需要同步”；已有说明中的启动与运行时并发描述也需核对时序。

<a id="flash-bank-edata"></a>

### 5.4 双 Bank 与 EDATA 参数布局

**本人补充的项目布局：程序放 Bank1，Bank2 末尾的 EDATA 用于参数保存。** 这是本轮新增的项目说明；确切参数地址、启用扇区数及 Option Bytes 尚未核验。另需与旧 Flash 说明的 QuadWord 版本对齐，见 [5.6](#edata-programming-check)。

STM32H563ZI 标称 2 MB Flash，分为两个各 1 MB 的 Bank。Bank 可以理解为芯片内部能配合执行读写操作的两个存储分区，不是两颗外接 Flash，也不是一个存程序、另一个就天然变成 EEPROM。

```text
片内 Flash（按本人描述的用途示意，不代表已核验链接地址）
├─ Bank1
│    └─ 应用、ThreadX、USBX、HAL 与业务代码
└─ Bank2
     ├─ 其他普通 Flash 空间
     └─ 末尾配置为 EDATA 的区域
          └─ PPS 开关、波特率等持久化参数
```

双 Bank 的重要能力是 RWW（Read-While-Write）：在一个 Bank 擦除或编程时，可以读取另一个 Bank。因此，把执行代码放 Bank1、把需更新的数据放 Bank2，有利于减少擦写参数对程序取指的影响。但驱动忙等、临界区、锁等待，以及对正在擦写 Bank 的其他访问，仍可能影响响应；不能说保存参数对实时性完全无影响。

EDATA 是 **Flash 的高耐久数据区**，不是额外附送的独立 EEPROM。对 H563ZI，每个 Bank 最多可将末尾 8 个扇区配置成高耐久数据区；配置后每扇区提供 6 KB 数据容量，每 Bank 最多 48 KB，两个 Bank 合计最多 96 KB。这些容量来自对现有 Flash 的配置，不是另加到标称 2 MB 上。

普通扇区为 8 KB，EDATA 模式使用不同的 ECC 组织后，可用数据容量为每扇区 6 KB；支持最小 16 bit 的数据编程粒度。若项目只启用最后一个扇区，对应的是 6 KB EDATA，而不是 48 KB，也不是整个 Bank2。

EDATA 通过 Option Bytes 中的 `EDATA1_EN`／`EDATA2_EN` 和 `EDATA1_STRT`／`EDATA2_STRT` 配置。启用后通过专用数据地址窗口访问；地址映射还与 Bank 交换配置有关，不能直接套用普通 Flash 末尾地址。EDATA 用于数据访问，不能作为普通指令执行区。

依据：[H563 数据手册 §3.4](https://www.st.com/resource/en/datasheet/stm32h563zi.pdf)、[ST AN4894 高耐久数据区说明](https://www.st.com/content/st_com/en/technical-documents/an4894-how-to-use-eeprom-emulation-on-stm32-mcus-stmicroelectronics_asset/chunk-003-topic-an4894-high-cycle-data-area-of-flash-memory.html)。

<a id="edata-vs-eeprom"></a>

### 5.5 EDATA 与 EEPROM 的区别

用途相似：都可保存掉电后仍需保留的小量参数。区别在于 EDATA 仍受 Flash 的擦除／编程规则约束，而常见专用 EEPROM 给应用提供字节写、页写等接口，内部完成相应写周期。

| 对比项 | H563 EDATA | 典型专用 EEPROM，以 M24C64 为例 |
| --- | --- | --- |
| 存储实现 | MCU 片内高耐久 Flash 区域。 | 独立 EEPROM 器件，通过 I2C 访问。 |
| 小量写入 | 支持最小 16 bit 编程粒度，需遵循对齐和编程规则。 | 提供字节写和页写接口。 |
| 擦除管理 | 仍按扇区擦除，需由软件保存其他有效数据并管理更新。 | 用户通常不需先发送整扇区擦除命令，器件内部执行写周期。 |
| 掉电保持 | 正常完成保存后可保留数据。 | 正常完成保存后可保留数据。 |
| 更新时掉电 | 需设计提交和恢复机制。 | 同样不能默认一组参数更新具有事务原子性。 |
| 类似 EEPROM 的接口 | 可由软件在 EDATA 上封装实现。 | 器件本身提供相应读写接口。 |

EEPROM 的“页写”也不等于 Flash 的“扇区擦除”：前者是一次写入多个字节的接口方式，具体页边界和内部更新单位由器件定义。参考 [M24C64 数据手册的写操作章节](https://www.st.com/resource/en/datasheet/m24c64-w.pdf)。

**启用 EDATA 不等于已经实现 EEPROM 仿真算法。** ST 的 X-CUBE-EEPROM 是在 Flash／EDATA 上提供记录管理、多页迁移、磨损均衡及掉电恢复的软件方案；当前项目是否采用该库，尚未确认，不能把这些能力直接写成已有实现。

### 5.6 EDATA 与 QuadWord：需要核对的版本差异

本人整理的《RCREADER_FLASH读写软件设计说明》第 9 页 §4.4 写明：采用标准 QuadWord、16 字节对齐写入，并屏蔽 EDATA 模式逻辑；第 10 页代码使用 `FLASH_TYPEPROGRAM_QUADWORD`。这与本轮补充的“实际使用 Bank2 EDATA”存在需要核对的配置／版本差异，目前不据此判定哪一个描述代表最终固件。

ST HAL 对两类编程路径作了区分：

```c
FLASH_TYPEPROGRAM_QUADWORD        /* 普通 Flash：128 bit，16 字节 */
FLASH_TYPEPROGRAM_HALFWORD_EDATA  /* EDATA：16 bit，2 字节 */
FLASH_TYPEPROGRAM_WORD_EDATA      /* 当前 HAL 还提供 EDATA 的 32 bit 编程路径 */
```

这是编程类型对照，不是可直接复制执行的写入代码。接口是否具备某个宏，以及对齐、地址和数据指针要求，需按项目 HAL 版本与手册确认，不能把普通 Flash 的 QuadWord 参数原样套到 EDATA。

确认实际方案需要一起看：

1. 参数区地址宏，如 `FLASH_PAGE_START_ADDR`，以及链接布局是否正确预留。
2. `EDATA2_EN`、`EDATA2_STRT` 和 Bank 交换等 Option Bytes。
3. `HAL_FLASH_Program()` 的实际 `TypeProgram` 及调用地址。
4. 擦除使用的物理 Bank、扇区号和配置后的数据容量是否一致。

**仅在 Bank2 最后留一个参数扇区，不等于已经启用硬件 EDATA。** 面试时应按核实后的版本说明。HAL 依据：[ST 官方 Flash 驱动](https://github.com/STMicroelectronics/stm32h5xx-hal-driver/blob/main/Src/stm32h5xx_hal_flash.c)。

<a id="flash-endurance"></a>

### 5.7 擦写寿命、计数单位与寿命预算

针对本芯片，可先记“普通 Flash 1 万次、EDATA 10 万次”；专用 EEPROM 常有百万次级指标，但必须看确切型号和条件，不能概括所有 Flash 或所有 EEPROM。

| 存储类型／型号 | 官方耐久度指标 | 条件与理解 |
| --- | --- | --- |
| STM32H563 普通程序 Flash | 10,000 次擦写循环。 | 数据手册表 52，结温范围 −40～+130°C 下的耐久度指标。 |
| STM32H563 高耐久数据区 EDATA | 100,000 次擦写循环。 | 同表规定条件下的数据存储区指标；必须确认启用了相应模式。 |
| Microchip AT24C64B EEPROM | 1,000,000 次写循环。 | 表 4-6：25°C、3.3 V、页写模式。 |
| ST M24C64 EEPROM | 4,000,000 次写循环；85°C 时为 1,200,000 次。 | 表 14：前者为环境温度不高于 25°C，电压处于规定范围；具体器件工艺和内部计数单位还需看注释。 |

来源：[H563 数据手册表 52](https://www.st.com/resource/en/datasheet/stm32h563zi.pdf)、[AT24C64B 数据手册表 4-6](https://ww1.microchip.com/downloads/en/DeviceDoc/AT24C64B-Data-Sheet-20006188A.pdf)、[M24C64 数据手册表 14](https://www.st.com/resource/en/datasheet/m24c64-w.pdf)。这些数值的测试／规定条件不同，不能脱离温度等条件做完全等价的倍数比较。

**不是整颗芯片共用一个“剩余写入次数”。** 对 Flash，主要关注同一个物理擦除扇区反复经历擦除、编程的次数；一个扇区被反复擦写，不会直接扣除其他未反复擦写区域的次数。EEPROM 则按厂家规定的字节、页或内部存储分组评估；例如带 ECC 的部分器件还涉及四字节分组，不能统一假设每次只磨损一个字节。

普通读取不计入这里的擦写循环；一次应用层“参数更新”也不一定等于一次物理擦除，取决于是否原位擦写、是否追加记录以及何时回收扇区。

下面假设**每保存一次，都擦除并重写同一个扇区**，仅按循环额度计算：

| 保存频率 | 普通 Flash：1 万次 | EDATA：10 万次 |
| --- | --- | --- |
| 每天 100 次 | 约 100 天。 | 约 1,000 天，约 2.7 年。 |
| 每分钟 1 次，全天运行 | 约 6.9 天。 | 约 69 天。 |

这是教学预算，不是本项目的实测保存频率，也不是某一天必然损坏。PPS 开关和波特率若只在用户修改配置时保存，频率可能很低；若每次通信甚至每次循环都保存，同一扇区的额度就可能很快用完。不能只用“10 万次看起来很多”来判断寿命。

擦写耐久度与数据保持时间不同：前者是可更新多少轮，后者是写完后能保存多久。温度和已经经历的循环次数会影响保持能力；高耐久也不等于无限期保持、抗任意掉电或免除校验。

<a id="flash-update-recovery"></a>

### 5.8 参数更新、磨损均衡与掉电恢复

若同一扇区有多个有效参数，修改其中一个时采用原位保存，需要保留全部其他有效内容：

```text
读出需要保留的有效参数 → 在 RAM 中修改目标字段
 → 擦除参数扇区 → 按对应模式编程完整有效参数
 → 检查返回值及保存结果 → 按约定返回成功／失败
```

“读一个参数，擦整个扇区，只写回这一个参数”可能丢失同扇区其他配置。即便已保存全部参数，这种单区读改擦写也有“旧数据已擦除、新数据尚未写完”的掉电窗口，不能直接宣称掉电安全。

可以考虑的优化方向，均未确认项目已经实现：

- 参数未变化就不写，合并短时间内的重复修改，减少无效保存。
- 在空白位置追加新记录，例如“版本、序号、参数、校验”，不在每次更新时都擦除。
- 使用不同擦除扇区保存新旧有效记录；新记录写入并校验、提交后，才允许回收旧记录所在扇区。不能把仅在同一扇区存两份记录直接当成完整掉电恢复。
- 有效提交标记按独立编程单元设计并最后写入，避免反复编程同一 ECC 单元；启动时按有效性和序号选择记录，处理写入中断和擦除中断。
- 定期迁移／轮换使用扇区，分散擦除次数，并测量最坏保存时延和失败恢复路径。

ST 的 [EEPROM 仿真方案 AN4894／X-CUBE-EEPROM](https://www.st.com/resource/en/application_note/dm00311483-eeprom-emulation-techniques-and-software-for-stm32-microcontrollers-stmicroelectronics.pdf)提供多页管理与相关软件机制，可作为学习参考，不能在未集成和验证时宣称项目具备同等保证。

面试时明确区分两个承诺：“正常保存完成后断电，重启能读回”证明了持久化；“擦除／编程任意时刻断电都能恢复有效配置”还需恢复算法、供电条件和针对性的断电测试证据。

## 6. CDC 到 USBX-CCID 迁移

这是简历中独立的一条工作线，不能把 CDC 工程说明直接当成最终 CCID 架构。

- CDC 提供虚拟串口通道，业务通常自行定义帧协议与组包。
- CCID 提供智能卡设备类命令与响应，主机请求进入设备类处理后再映射业务。
- 简历列出 `XfrBlock` 处理卡片传输、`Escape` 承载相应私有扩展；具体支持、权限、输入输出和缓冲区归属待核实。
- 迁移要检查设备描述符、端点、主机驱动、类回调、请求长度、卡槽状态和业务应答，不能只替换两个函数名。

### 6.1 “64 字节 Bulk 接收阻塞”怎样准备？

当前只能确认简历提出过这个问题，缺少故障日志与最终改动，**不能预先认定是少发 ZLP，也不能认定是 USBX 的 Bug**。

1. 先确认 USB 速度、端点最大包长，以及 64 指的是 USB 包、类消息、缓冲区还是实际业务长度。
2. 同时记录主机请求长度、设备请求接收长度和 actual length；区分 USB packet、一次 transfer 与完整 CCID 消息。
3. 在临界长度前后、以及最大包长整数倍附近对照，确认停在 USB 层、类层回调还是业务等待。
4. 核对协议声明长度、组包状态、缓冲区容量、超时与应答；是否需要短包／ZLP，要结合具体传输方向和结束条件判断。
5. 最终补“原始现象 → 日志证据 → 根因 → 修改 → 边界回归”，再写成亲历案例。

围绕简历中的“参与 ThreadX 多任务固件架构维护，根据读卡、NFC 巡检、USB 通信、Type-C 电源及状态检测等任务的实时性配置线程优先级、线程栈和独立内存池，梳理系统初始化及任务调度流程”整理。以下是可能的追问与回答思路，不是确定真题或已经完成的个人工作清单；具体配置和验证结果仍需结合工程确认。

### Q1. 读卡器有哪些线程，各自负责什么？

按已有说明，主要有六类：USB 接收、读卡命令处理、NFC 巡检、Type-C／PD 管理、USB 启停管理和状态指示。线程按职责分工，通过事件、队列和互斥锁协作，具体名称及优先级见 [线程划分](#thread-layout)。

### Q2. PC 发出读卡命令后，经过哪些线程？

以原 CDC 方案为例：USB 接收线程收集数据并拼成完整请求，通知命令处理线程；后者解析、访问卡片，再通过 USB 返回结果。CCID 阶段要按对应设备类处理流程说明，不能与 CDC 混为一谈。

### Q3. 架构是不是你设计的，你具体做了什么？

按已确认内容可回答：“这是公司已有的平台，我参与维护，梳理了初始化、线程分工、同步和命令处理链路，并整理成设计说明。”实际修改过的配置、代码和验证结果再单独说明，不把整个驱动平台说成自己从零实现。

### Q4. 你说的实时性，具体是什么？

就是某项工作必须在允许的时间内得到响应或完成。例如读卡命令不能无限等待，Type-C 事件需要及时处理，NFC 周期巡检通常允许一定延后。具体期限应来自产品要求；目前没有确认的毫秒数，不临时编造。

### Q5. 为什么按这个顺序配置优先级？

根据响应期限、业务影响和任务执行特点安排。已有说明中，Type-C 管理优先级较高，随后是读卡、NFC 和状态等线程；ThreadX 的优先级数值越小，优先级越高。顺序是否合理，还要结合执行时间和等待行为验证，不能只按“业务重要”排序。

### Q6. USB 接收线程优先级低，会不会接收不及时？

存在这个风险，不能只凭优先级下结论。读卡线程等待事件或外设时会让出 CPU，但还要确认 USB 缓冲能覆盖接收线程的最长调度延迟，并通过连续请求测试检查是否丢失或积压。高优先级处理线程也依赖接收线程先把数据交上来。

### Q7. Type-C 管理线程优先级高，是不是负责电源安全？

高优先级有助于及时处理连接状态和协议事件，但电源安全还依赖硬件保护、电源通路及软件策略。不能认为“线程优先级最高，就能保证电源安全”；应按原理图和控制流程说明软硬件职责。

### Q8. 最高优先级线程一直不阻塞，会怎么样？

在单核抢占式调度下，如果它持续就绪，低优先级线程可能长期得不到运行。因此事件驱动线程通常应在无事可做时阻塞等待，而不是循环查询。中断或更高优先级线程仍可能打断它；仅向同优先级线程让出执行机会，也不能解决低优先级线程饥饿。

### Q9. 读卡和 NFC 巡检共享 I2C，怎么保证重要业务？

已有设计是读卡路径允许等待锁，巡检尝试获取锁，失败就跳过本次。但还必须限制单次事务和持锁时间、配置超时，并核对优先级继承。“允许一直等”本身不代表及时性有保证；巡检已经持锁时，读卡线程仍需等待其完成或进入可恢复的失败路径。

### Q10. 静态优先级配置好了，就能保证实时性吗？

不能。锁等待、长中断、长临界区和外设超时都会增加响应时间。应测量从收到请求到完成响应的时间，覆盖高负载与异常场景，而不只是观察正常运行是否流畅。

### Q11. 每条线程的栈应该分配多大？

根据最深调用链、局部变量、库函数和上下文保存需求估算，再测试余量。USB 或协议处理线程可能调用更复杂的函数，但不能仅凭线程名称决定栈大小；实际分配值需查 `tx_thread_create()` 的参数或对应封装。

### Q12. 线程栈里面放什么？

通常包括自动局部变量、函数调用所需信息和保存的寄存器上下文，具体布局与编译器、移植有关。局部 `static` 数组不属于线程栈；`malloc()` 返回的内存也不属于线程栈，但保存地址的局部指针可能在栈上。

### Q13. 怎么确认栈够不够？

可查看调试器的线程栈统计，或利用栈填充模式分析历史使用量，同时覆盖大报文、错误处理和复杂调用路径。测到的只是已覆盖场景，需要保留余量，不能认为一次测试就证明永远不会溢出；没有测过的项目不能回答成已测过。

### Q14. 栈溢出会有什么现象，如何定位？

可能破坏相邻数据，表现为偶发异常、跑飞或 HardFault。定位时记录故障线程、栈指针和边界，检查历史栈使用量、大局部数组及调用链。还要排除普通缓冲区越界，不能一遇到 HardFault 就认定栈溢出。

### Q15. 在线程里定义一个很大的接收数组有什么问题？

例如自动局部数组 `uint8_t buf[4096];` 通常就需要约 4 KB 栈空间，可能超过线程栈预算。可考虑静态缓冲或从池中申请，但需要同时处理共享访问、生命周期和申请失败，不能只是换个存储位置。

### Q16. 独立内存池具体是什么？

就是给不同模块划出各自管理的内存区域。ThreadX 有用于不同大小申请的 Byte Pool，也有按固定块大小申请的 Block Pool；项目实际采用哪一种，要查 `tx_byte_pool_create()`、`tx_block_pool_create()` 或对应封装，不能只根据“内存池”三个字判断。

### Q17. 为什么分成业务、USBX、USBPD 多个池？

便于分别预算和观察模块占用，避免一个模块耗尽公共池后直接影响其他模块的分配。但空闲容量不一定能互相借用，可能出现一个池满了、另一个池还有余量的情况；容量划分需要与实际峰值需求匹配。

### Q18. 内存池容量怎么确定，申请失败怎么办？

根据同时存在的栈、对象、缓冲和峰值请求估算，再实测调整。之前说明里的约 10 KB、15 KB、5 KB 只是配置线索；申请失败必须检查返回值，按业务选择等待、拒绝请求或清理回退，不能继续使用无效指针。中断上下文不能阻塞等待内存。

### Q19. 分了独立池，越界写还会影响其他模块吗？

会。分池只是分配管理上的边界，没有访问保护时，错误指针仍可能写坏其他区域。要限制访问，还需正确配置 MPU、权限等机制，不能把“独立内存池”称为完整的故障隔离。

### Q20. 线程栈从哪里来，谁负责释放？

栈可以用静态数组，也可以从内存池申请，然后将地址和大小传给 `tx_thread_create()`。ThreadX 的线程删除操作不等于把应用提供的栈自动归还内存池；应用需要在确认线程已不再使用这些资源后负责回收，静态数组则不调用释放接口。不能在线程还使用该栈时回收它。

### Q21. 从上电到第一个线程运行，经历什么？

```text
复位启动
 → 建立栈、准备 C 运行环境
 → main 中进行前置硬件初始化
 → 进入 ThreadX
 → 创建应用资源和线程
 → 调度器选择就绪线程运行
```

具体硬件初始化放在哪一步，取决于工程设计。复位入口、C 启动与 `main()` 的先后关系不能省略成“上电直接执行线程”。

### Q22. main、tx_kernel_enter、tx_application_define 分别负责什么？

`main()` 是 C 程序入口，可完成前置初始化；`tx_kernel_enter()` 进入 ThreadX 并组织内核初始化；内核调用 `tx_application_define()`，由应用创建初始线程和资源。该回调返回后进入调度，`tx_kernel_enter()` 正常情况下不返回，所以不能把后续业务放在其调用之后等待执行。

### Q23. 线程、同步对象和外设按什么顺序初始化？

原则是使用者开始工作前，它依赖的资源必须准备好。通常先建立所需内存池、队列和锁，再让相关线程或外设数据流开始工作。如果在线程运行期间创建其他线程，还要注意新线程可能立即参与调度，必要时先挂起或等待启动事件；外设中断也不能在依赖资源尚未就绪时提前访问它们。

### Q24. 中断收到数据后，怎么让线程处理？

中断里完成必要的数据保存、状态确认和硬件标志处理，再通过事件、信号量或队列通知线程。只能调用 ThreadX 允许在中断中使用的服务，不能阻塞等待；中断退出后是否立即切换线程，还取决于优先级等调度条件。通知本身不等于保存了数据，缓冲区必须有明确的所有权和覆盖规则。
