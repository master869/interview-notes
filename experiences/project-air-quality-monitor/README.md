## 3. 传感器采样与可靠性

### 3.1 SGP30：为什么是 1 Hz？

从手册要求出发，确认初始化后是否按期发测量命令，结果是否过了启动阶段，是否采用基线／湿度补偿等功能。不能把读回一个数字就当成准确、稳定的环境结论；基线保存和补偿只有实际实现过才能写入项目成果。

需要补：器件是裸芯片还是带稳压／电平转换的模块、实际供电、7 位地址传参方式、命令等待、响应检查及错误恢复。未应答与总线被拉低是不同问题。

<a id="sgp30-crc-ack"></a>

#### 3.1.1 CRC 校验的是通信内容，不是测量精度

按 [SGP30 手册 §6.2、§6.3、§6.6／表 13](https://sensirion.com/en/media/documents/984E0DD5/61644B8B/Sensirion_Gas_Sensors_Datasheet_SGP30.pdf)，读取空气质量结果时，传感器返回的每个 16 位数据字都跟随一个 CRC-8 字节。因此，简历中的 CRC 可以对应 SGP30 测量结果的通信完整性检查；是否已经在项目驱动中执行、UART 是否另有 CRC，仍需原代码确认。

可以把 CRC 理解为按固定规则算出的数据“指纹”：传感器根据数据计算并附带 CRC，主控用收到的数据重新计算，再比较两个结果。如果不一致，本次数据存在错误，应标记无效并按采样策略安排后续读取。CRC 负责检错，不负责纠错，也不保证发现所有错误；即使通过，也不能证明传感器测量准确、数据最新或处于有效工作状态。

| 环节 | 检查什么 | 示例 |
| --- | --- | --- |
| CRC 校验 | 数据是否存在可检测的通信错误。 | 传输干扰导致位变化，重新计算的 CRC 与收到的值不一致。 |
| 状态检查／异常值过滤 | 已收到的数据是否适合用于业务。 | 检查初始化阶段、缺测、明显异常或需要进一步确认的跳变。 |
| 连续阈值判断 | 有效样本是否持续满足告警条件。 | 连续多个有效样本超限才进入报警状态。 |

处理顺序可组织为“读数据 → CRC → 状态／异常检查 → 更新有效样本 → 阈值判断 → 显示与上传”，这是解释职责的流程，具体项目实现待核对。

#### 3.1.2 六字节结果里面包含什么？

```text
rx[0]        rx[1]        rx[2]      rx[3]       rx[4]       rx[5]
eCO₂ 高字节  eCO₂ 低字节  CRC①       TVOC 高字节 TVOC 低字节 CRC②
```

CRC①只保护 `rx[0]、rx[1]`，CRC②只保护 `rx[3]、rx[4]`，不是对整帧 6 字节统一计算一次，也不把设备地址、ACK／NACK 加入这两个 CRC 的计算。

SGP30 规定的算法为 CRC-8：多项式 `0x31`（完整多项式为 `x^8 + x^5 + x^4 + 1`），初值 `0xFF`，输入／输出均不反射，最终异或 `0x00`；每个数据字独立从初值开始计算，高字节先处理。手册测试向量：两字节 `0xBE, 0xEF` 的 CRC 为 `0x92`。算法参数是器件协议要求，不是当前项目自定义的 UART CRC 参数。

```c
// 示意：I2C 已读入 rx[6]，crc8_sgp30() 按上述器件参数实现。
bool eco2_ok = crc8_sgp30(&rx[0], 2) == rx[2];
bool tvoc_ok = crc8_sgp30(&rx[3], 2) == rx[5];

if (!eco2_ok || !tvoc_ok) {
    // 示例策略：整次读取标为无效，不更新有效样本。
    return SENSOR_CRC_ERROR;
}

uint16_t eco2 = ((uint16_t)rx[0] << 8) | rx[1];
uint16_t tvoc = ((uint16_t)rx[3] << 8) | rx[4];
```

#### 3.1.3 “八位数据加一位应答”和 CRC 不冲突

8 位组成一个字节。上面的 6 字节指有效传输内容，其中已经包含两个 CRC 字节；在 I2C 线上，每个字节后面还各有第 9 个时钟的应答位，CRC 字节也一样。

```text
SGP30 发 8 位 eCO₂ 高字节 → 主控 ACK
SGP30 发 8 位 eCO₂ 低字节 → 主控 ACK
SGP30 发 8 位 CRC①        → 主控 ACK
SGP30 发 8 位 TVOC 高字节 → 主控 ACK
SGP30 发 8 位 TVOC 低字节 → 主控 ACK
SGP30 发 8 位 CRC②        → 主控 NACK → STOP
```

**读取阶段应答由主控发送。** 每个字节的前 8 个时钟由 SGP30 控制 SDA 发送内容，第 9 个时钟传感器释放 SDA，主控拉低表示 ACK、释放为高表示 NACK；SCL 由主控提供。前五个字节后 ACK 表示接受该字节并继续接收，最后一个字节后 NACK 是正常结束，不表示 CRC 错误。

地址阶段方向不同：主控先发送“7 位设备地址 + 1 位读写位”，由传感器应答。不要把地址阶段与后续读取数据阶段的发送方、应答方混淆。

结果的 6 字节阶段占 `6 × (8 + 1) = 54` 个 SCL 时钟，其中 48 个是内容位，6 个是应答位。这不包含设备地址阶段、前面的测量命令写入，以及 START／STOP。完整读取地址阶段再加 9 个时钟；不能把 54 当成从发命令到结束整个流程的总时钟数。

#### 3.1.4 为什么应用数组里没有 ACK／NACK？

通常 I2C 控制器与驱动负责产生应答，接收缓冲 `rx[6]` 只保存六个内容字节；应答位不会作为额外数据塞进数组。若使用软件 I2C，则需要底层驱动自己在第 9 个时钟处理应答。

| 对象 | 谁产生 | 作用 |
| --- | --- | --- |
| 数据字节后的 ACK／NACK（读取阶段） | 接收数据的主控。 | 总线传输的应答与继续／结束控制，不是数据内容正确性的证明。 |
| SGP30 结果中的 CRC 字节 | SGP30 计算并发送，主控重新计算检查。 | 对前两个数据字节执行内容检错。 |

所以主控可能已经正常 ACK，却在校验后发现内容错误；ACK 不能代替 CRC。最后的 NACK 也不能单独作为传感器故障统计。

#### 3.1.5 两种传感器、两段链路要分开

- **SGP30 → AVR：** I2C 数据按器件协议附带 CRC-8，主控应计算检查。
- **DHT11 → AVR：** 使用其单线协议与 8 位累加校验和，算法不是 CRC。
- **AVR → ESP32：** UART 数据重新封装后属于另一段传输；前面的传感器 CRC 不会自动保护它。是否另加 CRC、保护哪些字段和怎样处理错帧，需要查实际 UART 协议。

**面试可回答：** “SGP30 返回两个 16 位测量结果，各自附带一个 CRC-8 字节，所以应用读取六个字节。I2C 的每字节仍按八位内容加一位应答传输，CRC 字节也有自己的应答位；读数据时是主控发送 ACK，最后一个字节后 NACK 正常结束。CRC 检查内容传输错误，ACK 不能替代 CRC，CRC 通过后还要检查数据状态并做异常与阈值处理。”

### 3.2 DHT11：单总线时序与温湿度采集

**资料与事实边界：** 本节按奥松《DHT11 说明书》2022 年 12 月版 §5、图 5～11、表 6～7 解释工作原理。已核对手册波形，尚未取得本项目 DHT11 驱动源码，所以下面的引脚和函数示例用于回忆实现方式，不代表确认了当时的接线、计时方法或中断处理。实物版本不同，应以对应手册为准。

#### 3.2.1 “单总线时序”到底是什么？

这里只用一根 DATA 数据线传送请求和响应，不另接 SCL／SCK 时钟线；供电 VCC 和地 GND 仍然需要。可以理解成“主控和传感器轮流使用同一根线，通过电平持续多久表达信息”。

- **单总线**：主控请求与传感器返回的数据共用 DATA，交替控制线路。
- **时序**：规定谁先拉低、保持多久、何时释放，以及接收方何时检测电平。
- **数据位**：每位都包含低电平和高电平，靠高电平的长短区分 0、1；不是高电平本身就代表 1。

这属于器件规定的单线通信协议，可通过 GPIO 与计时逻辑实现；它不是 I2C，也不能当作 Dallas／Maxim 的 1-Wire 协议。DHT11 的一帧也没有可用来寻址不同传感器的设备地址，因此通常为每个 DHT11 分配独立数据引脚，不能像有地址的 I2C 器件一样直接并接并分别读取。

#### 3.2.2 接线和“释放总线”

```text
兼容的供电／逻辑电源 ── 上拉电阻（手册典型 4.7 kΩ）──┐
                                                  │
ATmega328PB 的一个 GPIO ────────────────────────── DATA ── DHT11
ATmega328PB GND ────────────────────────────────── GND ─── DHT11
```

DHT11 另接 VCC。裸器件与三针模块的引脚顺序可能不同，模块可能已带上拉，实际接线按实物确认。手册要求数据口采用开漏或三态方式：需要低电平时主动拉低，需要高电平时停止驱动，让上拉电阻把线路拉高，避免主控强推高电平而传感器同时拉低。

在 AVR 上可以通过“输出低／输入高阻”切换模拟这种行为。以下假设接 PD2，仅示意寄存器用法，实际引脚待核对，并假设已配合适的外部上拉：

```c
// 主控拉低：输出锁存先置 0，再把该位配置为输出。
PORTD &= ~(1U << PD2);
DDRD  |=  (1U << PD2);

// 主控释放：改成输入，外部上拉使总线恢复高电平。
// PORTD 对应位保持 0，不依赖内部弱上拉。
DDRD  &= ~(1U << PD2);

// 读取线路实际电平，读 PIN 寄存器。
bool data_is_high = (PIND & (1U << PD2)) != 0;
```

**释放不等于主控一直输出高电平。** “切成输入”是把控制权让给传感器，主控仍然可以读取 DATA 电平。AVR 寄存器行为见 [Microchip 数字 I/O 说明](https://developerhelp.microchip.com/xwiki/bin/view/products/mcu-mpu/8-bit-avr/structure/ioports/)。

#### 3.2.3 一次读取怎样进行？

| 阶段 | 谁控制 DATA | 按所引手册的时序 | 主控做什么 |
| --- | --- | --- | --- |
| 上电／空闲 | 双方释放，由上拉保持高 | 上电后至少等待 2 s。 | 初始化引脚和计时，暂不发起读取。 |
| 起始请求 | 主控 | 拉低 18～30 ms，典型 20 ms。 | GPIO 输出低，通知 DHT11 准备通信。 |
| 交接 | 主控释放 | 到传感器响应前约 10～35 μs。 | 改成输入，及时检测响应，不能长时间延时后才来观察。 |
| 应答 | DHT11 | 先低 78～88 μs（典型 83），再高 80～92 μs（典型 87）。 | 检查低、高及随后下降沿是否在限时内出现。 |
| 40 个数据位 | DHT11 | 每位先低 50～58 μs；随后用高电平长度表示 0／1。 | 逐位测量并组装 5 字节。 |
| 结束 | DHT11 后释放 | 最后一位后再低约 54 μs，随后线路回高。 | 完成校验、解析，维持释放状态。 |

```text
空闲高 → 主控拉低约 20 ms → 主控释放
 → DHT11 应答：低约 83 μs、高约 87 μs
 → 湿度字节 × 2 → 温度字节 × 2 → 校验字节
 → DHT11 结束并释放 → 主控检查结果
```

起始低电平是毫秒级，接收数据是微秒级，不能把两个单位混淆。读取的是数字结果，温湿度的物理测量和内部转换由 DHT11 完成，AVR 不需要再用自己的 ADC 测量 DATA。

#### 3.2.4 没有时钟线，怎么区分 0 和 1？

两种数据位的低电平前导相近，区别在后面的高电平：

```text
数据 0：低约 54 μs + 高 23～27 μs
数据 1：低约 54 μs + 高 68～74 μs
```

主控发现上升沿后开始计时，发现下降沿时结束计时，即得到高电平宽度。可在两个区间之间选判决门限，例如约 50 μs，短于门限解释为 0，长于门限解释为 1；这个门限是实现选择，不是传感器规定的额外命令。实际应结合计时误差及有效脉宽范围，拒绝明显异常的波形。

计时可用 GPIO 轮询配合硬件定时器；也可按可用引脚、外设设计边沿中断／输入捕获。另一种常见思路是上升沿后约 40 μs 采样，短高脉冲此时已结束而长高脉冲仍为高，但同样要求延时准确、状态同步正确。当前未确认项目使用哪一种。

**数据高位先发。** 逐位接收时，先把当前字节左移一位，再并入这次读到的位：

```c
bytes[i / 8] = (uint8_t)((bytes[i / 8] << 1) | bit);
```

这行只是把串行位流拼成字节，不会主动接收电平；`bit` 必须先由脉宽判断得到，`bytes` 初始应清零。

#### 3.2.5 40 位数据怎样变成温湿度？

| 字节 | 含义 |
| --- | --- |
| `bytes[0]` | 湿度整数部分。 |
| `bytes[1]` | 湿度小数部分，解释按实际版本。 |
| `bytes[2]` | 温度整数部分。 |
| `bytes[3]` | 温度小数／符号信息，解释按实际版本。 |
| `bytes[4]` | 前 4 字节累加结果的低 8 位。 |

教学例子：收到十进制 `[60, 0, 25, 0, 85]`，前四字节和为 85，校验一致，整数部分表示湿度 60 %RH、温度 25 ℃。这只是说明数据格式，不是项目实测记录。

```c
uint8_t checksum = (uint8_t)(bytes[0] + bytes[1]
                         + bytes[2] + bytes[3]);

if (checksum != bytes[4]) {
    return DHT_CHECKSUM_ERROR;  // 示例错误码
}

// 本例两个小数字节为 0，以下只展示整数部分。
uint8_t humidity_integer = bytes[0];
uint8_t temperature_integer = bytes[2];
```

这是 **8 位累加校验和，不是 CRC**，也不能发现所有可能的数据错误。简历中的 CRC 需要另核对 SGP30 响应校验或 UART 协议，不能说 DHT11 的最后一个字节采用 CRC。

旧版常见资料将 DHT11 小数字节写为保留或读出为零；本次引用的 2022 年版支持小数，温度低字节 Bit7 还表示符号。不能把 DHT22 的 16 位数值除以 10 的解析方式直接套过来。由于项目实物版本未确认，本笔记不写死通用于所有版本的完整温湿度换算函数。

#### 3.2.6 驱动函数应该怎样组织？

下面为 C 风格流程示例，`wait_level()`、`timer_us()`、延时函数与错误码需由项目实现，不是已找回的原始驱动。各个等待都必须有超时；计时器读取、回绕与精度也要处理。

```c
// bytes[5] 已清零；此前已等足上电时间和两次读取间隔。
dht_drive_low();
delay_ms(20);
dht_release();

// 检测应答低、应答高，再等到第一个数据位的低电平。
if (!wait_level(0, RESPONSE_TIMEOUT_US)) return DHT_TIMEOUT;
if (!wait_level(1, RESPONSE_TIMEOUT_US)) return DHT_TIMEOUT;
if (!wait_level(0, RESPONSE_TIMEOUT_US)) return DHT_TIMEOUT;

for (unsigned i = 0; i < 40; ++i) {
    if (!wait_level(1, BIT_TIMEOUT_US)) return DHT_TIMEOUT;
    uint16_t start = timer_us();

    if (!wait_level(0, BIT_TIMEOUT_US)) return DHT_TIMEOUT;
    uint16_t width = (uint16_t)(timer_us() - start);

    // 实际驱动还应检查 width 是否落在合理脉宽范围。
    uint8_t bit = (width > 50U) ? 1U : 0U;
    bytes[i / 8] = (uint8_t)((bytes[i / 8] << 1) | bit);
}

// 然后检查结束／释放状态、累加校验和，再更新有效样本。
```

`wait_level(level, timeout)` 表示“在限时内等到目标电平”；参数以真实微秒计时，不把空循环次数直接当作时间。若驱动修改了中断状态，所有成功和失败出口都应恢复原状态；示例省略了这些平台相关细节。

#### 3.2.7 这个项目尤其要注意的时序与异常

- **接收超时：** 传感器断线、引脚接错或线路卡住时，不允许 `while (DATA == ...)` 无限等待；应返回无响应、接收超时、校验失败等状态。失败后保留上一份有效数值时，应同时标注时间与过期状态。
- **中断干扰：** 数十微秒的高脉宽可能被耗时中断打断，导致错误判位。不是一律全程关中断；若软件接收确实需要屏蔽，应限制在必要窗口，起始的约 20 ms 低电平不必因此全部屏蔽，并评估接收窗口内数毫秒屏蔽对 UART、定时节拍的影响。可以再考虑捕获／边沿计时方案，而不是让其他模块承担丢数据风险。
- **延时精度：** 若使用 AVR 忙等延时，编译的 `F_CPU`、实际系统时钟和优化设置必须匹配；定时器方案要确认分频和计数单位，不能仅凭函数叫 `delay_us()` 就认为准确。
- **电气与诊断：** 先确认电源、共地、上拉和引脚输入模式，再用示波器／逻辑分析仪看“起始 → 应答 → 40 位 → 结束”。无应答与有波形但校验失败是不同定位方向。
- **1 Hz 与器件周期分开：** 所引手册规定上电后至少等待 2 s，两次通信至少间隔 2 s；并说明读出的是此前采集的结果，通信结束后再进行下一次采集。可将 SGP30／系统处理安排为 1 Hz、DHT11 至少每 2 s 读取一次，中间显示最近有效值和时间戳。这是建议方案，项目当时是否已分别调度仍待源码确认；不能把“通信完成很快”当成“可以每秒获取一份新的温湿度”。

**面试可回答：** “DHT11 由一个 GPIO 按器件的单线时序读取。主控先拉低约 20 ms，再释放线路，确认传感器应答，然后根据 40 个数据位的高电平宽度判断 0、1，高位先收并拼成 5 字节。前四字节是温湿度，最后一字节是累加校验和。驱动还要处理超时、微秒计时及中断影响，读取周期按实际器件手册安排。我会结合原始驱动再确认当时具体采用的计时方法。”

### 3.3 数据有效性与报警

建议解释为“每个样本有数值、单位、采样时刻和有效性”，但结构与实现待代码确认。异常值过滤、连续阈值判断不是一回事：前者处理测量异常，后者防止单次波动频繁报警。若每秒一次且要求连续 N 个有效样本超限，检测延迟与 N 有关；缺测是否清零计数、退出报警是否有回差，应按实际逻辑说明。

记录过期值与当前值需要区分；传感器断线不应无限显示最后一条读数却不标记异常。

## 4. LCD、报警与 SPI 共享

**事实边界：** 简历确认通过 SPI 驱动 ST7735 LCD，显示环境数值、状态与动态柱状图。以下总结 SPI 和显示控制原理；实际屏幕型号后缀、模块引脚、分辨率、颜色格式、主控时钟、SPI 模式／频率及刷新实现尚待原代码与原理图确认。计算与流程示例不作为项目实测或已实现优化。

### 4.1 SPI 基础：片选、时钟与逐位传输

SPI 是同步串行接口：主控产生时钟，设备在约定边沿采样数据。常见信号如下，通常一个设备对应一根独立片选：

| 信号 | 方向与职责 |
| --- | --- |
| SCK／SCLK | 主控输出，提供传输时钟。 |
| MOSI | 主控向从设备发送内容。 |
| MISO | 从设备向主控返回内容；是否接出和使用取决于器件与业务。 |
| CS／SS | 主控选中设备，常见为低有效，仍以器件定义为准。 |

例如高位先发送 `0xA5`，主控选中设备后依次输出 `1 0 1 0 0 1 0 1`，配合 8 个时钟传完一个字节。通用全双工 SPI 可以在相同的时钟内收、发数据；写屏业务可以只使用发送方向，但这不表示所有 SPI 都只能单向传输。

SPI 基础传输没有 I2C 那种“每字节第 9 位 ACK／NACK”，也不统一规定设备地址或 CRC；设备选择通常靠片选，更高层的命令、状态、校验等由具体器件协议规定。显示屏和 SD 卡虽然都能使用 SPI，命令含义仍不同。

### 4.2 CPOL／CPHA：在哪个边沿读取？

CPOL 决定时钟空闲电平；CPHA 决定从空闲开始的第一个还是第二个边沿采样。主控设置必须满足所选设备的时序要求。

| 模式 | CPOL | CPHA | 空闲电平 | 采样边沿 |
| --- | --- | --- | --- | --- |
| Mode 0 | 0 | 0 | 低 | 上升沿。 |
| Mode 1 | 0 | 1 | 低 | 下降沿。 |
| Mode 2 | 1 | 0 | 高 | 下降沿。 |
| Mode 3 | 1 | 1 | 高 | 上升沿。 |

以 Mode 0 为例，首位应提前准备好，随后在下降沿更新下一位、上升沿采样，保证采样边沿附近数据稳定。项目实际采用哪种模式需查配置，不能仅凭“使用 ST7735”记成某个固定值。

时钟频率同时受主控分频能力、从设备时序和板级信号质量限制。ATmega328PB 主机 SPI 分频表包含 `fosc/2` 等选项；这不等于项目实际已经使用最高速，也不等于显示吞吐率没有函数及字节间隙开销。

### 4.3 屏幕接口：CS、DC、RST 分别做什么？

以 ST7735 常见四线串行写入方式为例：

| 模块信号 | 作用 |
| --- | --- |
| SCK／SCL | 时钟；屏幕标为 SCL 也不必然代表 I2C。 |
| SDA／DIN／MOSI | 主控发出的串行内容，实际名称按模块确认。 |
| CS | 选择这块显示控制器。 |
| DC／A0 | `0` 表示命令字节，`1` 表示命令参数或像素数据。 |
| RST／RES | 控制器硬件复位，不是每传一个字节都要复位。 |
| BL／LED | 背光控制，是否引出以及驱动方式按模块确认。 |

**CS 选设备，DC 解释内容。** CS 拉低不表示后续一定是像素，DC 高也不一定是像素，还可能是设置地址等命令的参数。

ST7735 手册的“四线串行”指 CS、时钟、串行数据和 DC，不等于通用 SPI 示意图中的 SCK、MOSI、MISO、CS。显示模块可能未引出可用的读回路径；主控仅写命令和像素时，不一定需要 MISO。具体引脚用途与电压兼容性需对应实物，不能根据同名接口推断模块可直接承受 MCU 的任意逻辑电平。

### 4.4 从温度数字／柱状图到像素

```text
复位、按模块要求初始化 → 设置方向和像素格式
 → 选择更新矩形 → 发送像素 → ST7735 保存并驱动 LCD
```

ST7735 典型绘图命令为 `0x2A`（列地址／X 范围）、`0x2B`（行地址／Y 范围）、`0x2C`（开始写显示 RAM）。设定窗口后按当前配置的地址递增方向连续发送像素；通常无需为每个像素都重新设置坐标。坐标偏移和初始化参数可能随面板／方向变化，不直接复制其他模块的数值。

若采用 RGB565，每像素由红 5 位、绿 6 位、蓝 5 位组成，共 16 位、2 字节。颜色格式、像素字节顺序、RGB／BGR 顺序以及 SPI 字节内的 MSB／LSB 位序是不同概念；配置或封装出错都可能产生颜色异常。

显示字符串通常是绘图层查字库，将字符展开成像素，再通过屏幕驱动写入；不是把 ASCII 字符直接交给 ST7735 就自动出现文字。柱状图则把测量值映射成长度／高度，裁剪到绘图区域，按颜色绘制矩形。可按“业务显示 → 字库／图形 → ST7735 命令与窗口 → SPI 字节传输”解释分层，个人编写和复用边界另查源码。

### 4.5 只有 2 KiB SRAM，为什么能显示彩屏？

ATmega328PB 的 SRAM 为 2 KiB；ST7735 自带显示 RAM，所以 AVR 不必在自身 RAM 中保存整幅画面。可以边生成边发送像素、使用小块缓冲，并复用缓冲空间；字库的存储和读取还应按 AVR 的程序存储访问方式与实际库实现核对。

**教学计算，未确认项目采用该分辨率／格式／频率：**

```text
128 × 160 像素，RGB565：整屏数据 = 128 × 160 × 2 = 40960 B = 40 KiB
128 像素宽的一行：128 × 2 = 256 B
若 SPI 为 4 MHz：纯像素发送时间 = 40960 × 8 / 4000000 ≈ 82 ms
```

40 KiB 整屏 framebuffer 无法放入 2 KiB SRAM。即使只用一行 256 B，也要为 UART、SD 缓冲、业务变量及栈留下空间，不能把全部 SRAM 都用于显示。82 ms 只是不含命令、字形生成和驱动间隙的理论下限，不是项目帧率或实测阻塞时间。

### 4.6 刷新、共享总线与采样协作

适合环境数值与柱状图的优化方向：

- 固定标题、单位、边框初始化时绘制；变化区域再更新。
- 避免每轮清整屏再重画；数字宽度缩短时，清理或覆盖旧字符残留区域。
- 连续像素批量发送，减少反复设置窗口及函数／片选操作；DC 和 CS 切换应等待相应字节真正发送完成。
- 大区域可分块处理，在适当边界返回主循环服务采样和 UART；是否可暂停及怎样恢复写入，应按控制器协议和驱动实现处理。

若 LCD 与 SD 共用同一个 SPI 控制器，应使用独立 CS，切换前确保前一笔传输结束、取消片选，并按设备设置模式、频率和位序；未选中设备也必须正确释放共享返回线路。是否共用同一控制器、是否只在 Bootloader 阶段访问 SD，当前均待确认，不能凭“项目里都用了 SPI”认定存在运行时竞争。

刷屏耗时会影响主循环调度，长时间屏蔽中断还可能影响 UART 接收与定时；有硬件 SPI 不代表整个显示函数非阻塞。SPI 的时钟通常可以在满足器件要求的情况下暂停；不能仅因需要满足时序，就一概屏蔽整个 SPI 传输窗口。

声光报警的输出引脚、电流驱动和持续时间应由实际电路确认；耗时蜂鸣流程也要与周期采样协调。以上刷新优化属于建议，未确认项目已实现或取得特定性能提升。

## 5. 自定义 UART 与 ESP32 上传

### 5.1 项目目标、分工与参考方案边界

**本人确认：** ATmega328PB 将温湿度等环境信息传给 ESP32，ESP32 再经 Wi-Fi 上传云端展示。具体 UART 协议代码由队友实现，本机没有完整源码，原始帧格式与测试记录暂未找回。

**本节为重新设计的参考方案，便于理解与解释，不代表当时已经采用。** 帧头、长度、类型、序号、字节序、CRC 参数和异常策略均为本次示例约定；不据此声称本人独立编写了原协议。温湿度是本轮讨论的核心，示例同时容纳简历中的 eCO₂ 与 TVOC，实际需要时可以简化。

```text
传感器 → AVR：采样、有效性检查、打包
 → UART 字节流 → ESP32：组包、校验、还原记录
 → 按实际云端接口组织消息 → Wi-Fi 上传 → 展示
```

UART 本身传输字节，不知道哪一组字节表示一份采样记录，也不知道字段、单位和新鲜度；自定义协议是双方共同遵守的数据解释规则。

### 5.2 UART 硬件格式与应用数据帧分开

| 层次 | 本示例约定 | 解决的问题 |
| --- | --- | --- |
| UART 硬件 | 9600 波特率、8N1，双方匹配，实际波特率误差需核对时钟配置。 | 一个字节如何在线路上传输。 |
| 应用数据帧 | 16 个二进制字节，包含帧头、类型、长度、数据和 CRC。 | 哪些字节属于一份记录，以及怎样解释和检查。 |

8N1 是 8 个数据位、无奇偶校验、1 个停止位，另有 1 个起始位，因此每字节在线路上占 10 位；UART 硬件处理这些起止位，应用缓冲保存的是内容字节。普通 UART 不自带 I2C 式的逐字节 ACK／NACK，应用需要应答时应另定义消息。

接线需要 TX 接对方 RX，双向通信再接反方向，并共地；确认逻辑电平兼容，若 AVR TX 为 5 V，应适配后再接 ESP32 RX。实际板卡供电、接口引脚和电平转换电路待确认，不把逻辑 UART 与 RS-232 电平直接混用。

### 5.3 一套固定 16 字节的环境数据帧

```text
帧头 | 类型 | 长度 | 序号 | eCO₂ | TVOC | 温度 | 湿度 | 状态 | CRC
 2B     1B     1B     1B     2B     2B     2B     2B     1B     2B
```

| 位置 | 字段 | 示例定义 |
| --- | --- | --- |
| 0～1 | 帧头 | 固定 `0xAA, 0x55`，用于寻找候选帧起点。 |
| 2 | 类型 | `0x01` 表示本版环境记录。 |
| 3 | 数据区长度 | `0x0A`，即序号到状态共 10 字节；不包含帧头、类型、长度和 CRC。 |
| 4 | 序号 | 每发一帧递增，8 位无符号，255 后回到 0。 |
| 5～6 | eCO₂ | `uint16_t`，ppm。 |
| 7～8 | TVOC | `uint16_t`，ppb。 |
| 9～10 | 温度 | 16 位有符号补码，单位 0.1 ℃。 |
| 11～12 | 湿度 | `uint16_t`，单位 0.1 %RH。 |
| 13 | 状态 | 有效性及温湿度更新标志，见下文。 |
| 14～15 | CRC-16 | 保护字节 2～13，共 12 字节，CRC 低字节先传。 |

所有多字节字段统一低字节先传。比如 650 为 `0x028A`，线上发送 `8A 02`；25.3 ℃ 编码为整数 253，即 `FD 00`。负温度按有符号补码编码，接收端也必须按有符号数解释。单位缩放为 0.1 ℃ 不代表传感器精度达到 0.1 ℃，也不把这当作实际 DHT11 测试结果。

```c
// 示例：发送方显式拆字节，接收方按约定重组。
frame[5] = (uint8_t)(eco2 & 0xFFU);
frame[6] = (uint8_t)(eco2 >> 8);

uint16_t eco2_received = (uint16_t)frame[5]
                      | ((uint16_t)frame[6] << 8);
```

不直接发送整个 C 结构体的内存，避免填充、字段宽度和布局差异。发送的是二进制 `0xAA` 等字节，而不是打印字符 `'A'`、`'A'`；同时区分“16 位数的字节序”和 UART 硬件在一个字节内部的位序。

### 5.4 状态：区分无效、新采样与缓存值

| 状态位 | 为 1 表示 |
| --- | --- |
| bit0 | 本次携带的 eCO₂／TVOC 数据有效且未过期。 |
| bit1 | 本次携带的温湿度有效且未过期。 |
| bit2 | 温湿度是本轮新成功取得的数据，而非沿用缓存。 |
| bit3～7 | 保留，发送时为 0。 |

例如系统每秒发送一帧，但 DHT11 根据手册至少间隔 2 s 读取：新读取成功时 bit1、bit2 都置位；中间帧可带仍有效的缓存值，bit1 置位、bit2 清零。超过约定有效期后清除有效位，不能无限沿用旧值。具体过期门限属于需要双方定义的业务参数，未在原项目中核实。

无效字段的数值不应用于正常显示或报警；接收端应按状态标记缺测／过期。当前帧没有携带各传感器采样时间，若需要准确的数据年龄，可在后续新格式中增加时间戳或年龄字段，不能仅靠帧发送序号证明测量新鲜。

### 5.5 CRC 与一条完整报文

参考方案借用 CRC-16/MODBUS 算法，不表示采用整套 Modbus 协议。参数为：初值 `0xFFFF`，标准多项式 `0x8005`、右移实现使用 `0xA001`，输入／输出反射，最终异或 `0x0000`；CRC 结果低字节先发。只计算字节 2～13，不包含帧头、CRC、自带的 UART 起始／停止位。

教学记录：序号 1、eCO₂ 650 ppm、TVOC 120 ppb、温度 25.3 ℃、湿度 60.4 %RH、状态 `0x07`。完整帧为：

```text
AA 55 | 01 | 0A | 01 | 8A 02 | 78 00 | FD 00 | 5C 02 | 07 | 62 00
```

按上述范围计算 CRC 为 `0x0062`，所以附加 `62 00`；这个示例已核算，不是找回的原项目抓包。算法的常用检查向量为 ASCII `123456789` 得到 `0x4B37`，用于检查实现参数是否一致。

SGP30 的 CRC-8 保护传感器到 AVR 的数据，UART 这里的 CRC-16 保护重新封装后的板间记录，两者作用于不同链路。CRC 负责检错，不纠错，不保证送达，也不能证明云端已展示；通过后仍要检查状态和数值含义。

### 5.6 ESP32 持续组包与错误恢复

一次 `read()` 不保证拿到一整帧：可能只得到前 5 字节，也可能一次得到多帧。应按字节流持续解析，而不是认为“UART 一次接收等于一次采样”。

```text
读取字节到有界缓冲
 → 搜索 AA 55 → 检查类型 01、长度 0A
 → 不足 16 字节则等待后续数据
 → 收齐后计算并比较 CRC
 → 通过：解析字段，检查有效状态，更新记录，消费该帧
 → 失败：从候选帧第二个字节继续搜索，寻找重新同步机会
```

- **有界接收：** 当前版本只接受规定类型和 10 字节数据区；候选帧上限 16 字节，不根据错误长度无限等待或分配。实际串口接收缓冲还需按调度延迟与流量安排容量。
- **接收超时：** 半帧长期收不齐时放弃当前候选并重新同步，门限需大于正常发送间隙并考虑接收调度，不能把任意一个常数当作原项目参数。
- **帧头重合：** 数据区本身可以出现 `AA 55`。已开始收集候选帧后按长度处理，不是一看到该字节组合就立即重启；CRC 失败再滑动搜索，避免忽略候选帧内部可能存在的真正帧头。
- **序号检查：** 辅助统计丢帧、重复及顺序异常，注意模 256 回绕；设备重启也可能归零，因此它不是全局唯一记录号，不能只凭序号跳变精确判定所有丢包。
- **驱动错误：** UART 帧错误、硬件溢出或软件缓冲溢出应记录，并触发必要的丢弃／重新同步，不能只统计 CRC。

ESP32 Arduino 中 `available()` 给出当前可读字节数，`read()` 返回字节或本次读到的数量，应用协议需要自行组包；`readBytes()` 还可能等待至超时，不能默认一定完整返回。

### 5.7 上传、应答与验证策略

ESP32 解包后还原单位，再按实际云端接口组织消息。Arduino 框架不决定采用哪个云平台或 HTTP／MQTT；原项目的目标、认证、连接恢复和上传确认仍待找回。

接收解析应持续得到运行机会，与可能耗时的联网操作分开。若 Wi-Fi 上传长时间阻塞同一处理路径，串口缓冲可能溢出；可采用独立接收执行路径、非阻塞联网状态机或有界工作方式，按实际框架选择。

对“展示当前环境”的最小方案，可以只保留最近有效记录：AVR 每秒主动发送，ESP32 丢弃坏帧并统计错误，下一有效帧更新，长时间没有有效数据则标记离线／过期。若上传侧与接收侧并发访问同一记录，快照交接也需保护，不能把多字段整体更新默认当作原子操作。

```text
9600、8N1 下：16 字节 × 10 位 / 9600 ≈ 16.7 ms／帧
```

这只是连续发送的线路占用，不包含采样、排队与云端耗时。周期环境展示可先不做应用 ACK／重传；代价是不保证每条采样都保留。若要求逐条可靠存储或下发必须执行的命令，需另定义 ACK、超时、有限重传、去重及重启行为，避免用“CRC 通过”代替送达确认。

验证应覆盖已知报文、错 CRC、错长度、截断、连续多帧、数据含帧头、断线及重启；统计有效帧、错误、序号异常、缓冲溢出和数据年龄。原简历中的持续运行验证应补实际时长、样本量与网络条件，未找回前不填“零丢包”或性能提升数字。

**分工表述参考：** “项目通过 UART 将 AVR 采集的数据交给 ESP32 联网上传，具体协议代码由队友实现。我理解组包、校验和解析的原理。当前这套 16 字节格式是复盘用的参考设计，原始格式需要查队友代码；我个人负责的采集、接口对接或联调部分按实际分工展开。”

## 6. SD 卡 Bootloader 更新

### 6.1 必须与 STM32 启动方式区分

ATmega328PB 是 AVR，不能套用 Cortex-M 的初始 MSP、VTOR 和 Reset_Handler 跳转流程。器件提供 Boot Loader Section、自编程 SPM、相关熔丝和锁定位；实际 Bootloader 链接位置、大小、复位入口和保护配置需要核对。

在这个方案中，SPI 用于从 SD 卡读文件；向 MCU 内部 Flash 写入则使用器件自编程机制，不是“经 SPI 直接写内部 Flash”。

### 6.2 简化更新流程及实现边界

```text
复位 → Bootloader 判断更新条件
 → 找到并检查镜像 → 分块读取
 → 按应用 Flash 页擦除／编程 → 读回或校验
 → 记录更新结果 → 按 AVR 要求启动应用
```

以上是需要与源码逐步对上的说明，不代表所有校验与提交步骤都已实现。重点追问：SD 使用文件系统还是固定扇区？库占多少 Flash/RAM？镜像怎样限制到应用区？最后不足一页如何处理？缺卡、读失败和中途断电后怎样恢复？

若只有一份应用镜像，写到一半可能破坏旧应用；只要 Bootloader 保持有效，也许能重新更新，但不能直接声称具备自动回滚。CRC 检测意外损坏，也不能代替固件签名验证。

### 9.2 SPI 与 ST7735 可能追问

下面是回答方向，具体模式、频率、引脚、刷新算法及性能按项目代码与记录回答。

| 可能的问题 | 简短回答／展开要点 |
| --- | --- |
| 为什么屏幕用 SPI？ | 显示要连续传输大量像素，SPI 适合批量传输，该模块也支持此接口。结合带宽、引脚与模块选型解释，不只说“比 I2C 快”。 |
| SPI 用哪几根线，为什么屏幕可以没有 MISO？ | 通用信号为 SCK、MOSI、MISO、CS；显示主要向屏幕写入，模块不一定引出读回线路。实际接线应列出 DC、RST 等辅助信号。 |
| 屏幕“四线 SPI”和普通 SPI 四根线一样吗？ | 不一定。所引 ST7735 手册的四线为 CS、SCL、SDA、DC，不是通用示意图中的 SCK、MOSI、MISO、CS。 |
| DC 和 CS 有什么区别？ | CS 选设备；DC 低表示命令，高表示参数或像素。用设置窗口、开始写像素的过程举例。 |
| 你配置了哪个 SPI 模式，如何确定？ | 根据主从时序匹配 CPOL／CPHA，检查空闲电平及采样边沿，并从实际初始化代码确认，不猜固定模式。 |
| SPI 时钟越高越好吗？ | 同时满足主控分频、屏幕时序、板级信号质量；实际吞吐还受处理和字节间隙限制。频率提高后应检查波形及可靠性。 |
| SPI 也有逐字节 ACK 或 CRC 吗？ | 基础 SPI 不规定 I2C 式第九位应答，也不统一规定 CRC；是否有状态／校验由器件的上层协议决定。 |
| 硬件 SPI 和软件 SPI 有什么区别？ | 硬件外设负责移位与时钟生成，软件 SPI 由 GPIO 操作模拟；后者更依赖 CPU 与时序实现。项目实际用法需看驱动，硬件 SPI 的轮询发送也可能阻塞 CPU。 |
| 怎么画一个矩形？ | 设列范围、行范围，发 RAM 写命令，再按像素格式连续发送该区域颜色；窗口和数据量要一致。 |
| 怎么显示温度数字，能直接发 ASCII 吗？ | 图形屏通常由字库／绘图层把字符转成像素，再经 ST7735 驱动写入；SPI 只负责传字节，不解释字符。 |
| RGB565 是什么，为什么可能颜色不对？ | 每像素红 5／绿 6／蓝 5 位，共 2 字节；检查像素格式、RGB／BGR、像素高低字节及 SPI 位序，不能把这些概念混为一谈。 |
| 2 KiB SRAM 怎么显示彩屏？ | 依靠屏幕内部显示 RAM，边生成边写或使用小块缓冲；128×160 RGB565 整屏需 40 KiB，只是教学例子，不能在 AVR SRAM 中整帧保存。 |
| 动态柱状图闪烁或有残影怎么办？ | 检查是否反复清屏、先擦后画及更新区域不足；局部覆盖变化范围，数字变短时清理旧内容，测量实际效果。 |
| LCD 和 SD 能否共用 SPI？ | 可以共享数据与时钟、分别片选，按设备切换配置并保证事务完整；先确认实际接线及 SD 是否只在 Bootloader 使用，不凭名称推断竞争。 |
| 刷屏会影响 1 Hz 采样或 UART 吗？ | 长时间阻塞会拖延主循环，关中断可能丢接收数据；分块刷新、控制每轮工作量并测最坏延迟，而不是只按 SPI 标称速率判断。 |
| 背光亮但白屏／无画面，怎么查？ | 背光亮只证明部分供电工作。按供电和逻辑电平、复位／初始化、CS／DC、时钟与数据、窗口／像素格式逐层看，先试固定纯色图案。 |
| 画面偏移、旋转或缺边，怎么查？ | 核对面板有效分辨率、地址偏移、方向控制和窗口边界；同系列控制器不同模块的初始化表不一定相同。 |
| 你自己写了哪一层？ | 按“业务 UI、字库／图形、ST7735 控制命令、SPI 底层”说明个人修改和库复用边界，并给实际函数，不能把调用库说成整套驱动从零实现。 |

### 9.3 UART 参考协议与联网链路可能追问

| 可能的问题 | 简短回答／展开要点 |
| --- | --- |
| UART 已经能传字节，为什么还要协议？ | 协议约定记录边界、字段、单位、顺序与校验；UART 起止位只处理单个字符，不能识别一份环境记录。 |
| 原协议是不是你写的？ | 具体代码由队友实现；16 字节格式是当前复盘参考，不冒充原始设计。个人采集、接口对接及联调内容按真实分工说明。 |
| 能举出一条完整报文吗？ | 用 [参考协议](#uart-reference-protocol)的 16 字节示例逐项解释，明确它是教学报文，原项目抓包待找回。 |
| 为什么用二进制，不直接传字符串？ | 固定二进制开销小、缓冲有界；文本方便调试且低速场景也可行。按实际资源与可维护性取舍。 |
| 固定 16 字节，为什么保留长度？ | 用于格式检查和后续不同消息类型的扩展；当前类型仍严格要求长度 10，不接受任意长度。 |
| 为什么不直接发送 C 结构体？ | 避免填充、字段宽度与布局差异，明确逐字段序列化；温度还需约定符号与缩放。 |
| 低字节先发是什么意思？ | 比如 650 为 0x028A，发 8A 02；这是多字节字段的顺序，不等于改变 UART 字节内部的位序。 |
| 帧头出现在数据里怎么办？ | 按长度收候选帧，收齐再校验；失败时滑动重同步，不在每次出现 AA 55 时无条件重启。 |
| 一次只收到半帧，或者收到多帧怎么办？ | 持续解析字节流，保留不完整候选，循环消费完整帧，并有超时与容量上限。 |
| CRC 检查哪里，用什么算法？ | 本示例采用 CRC-16/MODBUS 算法，仅保护字节 2～13，结果低字节先发；不是原项目参数，也不是整套 Modbus 协议。 |
| SGP30 已有 CRC，为什么 UART 再加？ | 两段链路不同，重新打包后的记录也需检查板间传输错误；CRC 不保证云端送达。 |
| 序号能判断丢包吗？ | 能辅助检测，但要考虑 8 位回绕、重复和设备重启，不能当作全局唯一编号或仅靠它精确解释全部异常。 |
| DHT11 不是每秒更新，帧里的值怎么处理？ | 区分仍有效的缓存与本轮新采样，用状态位与过期规则表示；不能把每秒发帧当成每秒新测量。 |
| 为什么可以不加 ACK？ | 当前环境展示可接受丢弃坏帧、下一帧覆盖，但不保证逐条保存；可靠记录或控制命令要补应答、有限重传与去重。 |
| Wi-Fi 断开或上传阻塞怎么办？ | 串口接收仍需持续处理；按需求保留最近值或使用有界记录缓存，并定义溢出、过期与恢复策略。 |
| 两板连接要注意什么？ | 交叉 TX／RX、共地、波特率和 8N1 一致，确认电平兼容；不要把逻辑 UART 当作 RS-232 电平。 |
| 怎么证明通信稳定？ | 已知向量核对加错误注入，统计有效帧、CRC／长度／硬件错误、缓冲溢出和序号异常；持续时长与结果必须有实际记录。 |
