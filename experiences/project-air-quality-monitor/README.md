依据 `resume(3.1).pdf`：使用 SGP30、DHT11 进行环境采集，ST7735 LCD 显示与声光报警，UART 向 ESP32 发送数据，ESP32 基于 Arduino 框架联网上传，并设计 SD 卡 Bootloader 更新。当前未阅读完整源码和原理图；本笔记不预设云平台、具体帧格式、CRC 参数或升级回滚已实现。

## 3. 传感器采样与可靠性

### 3.1 SGP30：为什么是 1 Hz？

从手册要求出发，确认初始化后是否按期发测量命令，结果是否过了启动阶段，是否采用基线／湿度补偿等功能。不能把读回一个数字就当成准确、稳定的环境结论；基线保存和补偿只有实际实现过才能写入项目成果。

需要补：器件是裸芯片还是带稳压／电平转换的模块、实际供电、7 位地址传参方式、命令等待、响应检查及错误恢复。未应答与总线被拉低是不同问题。

### 3.2 DHT11：单总线时序与温湿度采集

**资料与事实边界：** 本节按奥松《DHT11 说明书》2022 年 12 月版 §5、图 5～11、表 6～7 解释工作原理。已核对手册波形，尚未取得本项目 DHT11 驱动源码，所以下面的引脚和函数示例用于回忆实现方式，不代表确认了当时的接线、计时方法或中断处理。实物版本不同，应以对应手册为准。

#### 3.2.1 “单总线时序”到底是什么？

这里只用一根 DATA 数据线传送请求和响应，不另接 SCL／SCK 时钟线；供电 VCC 和地 GND 仍然需要。可以理解成“主控和传感器轮流使用同一根线，通过电平持续多久表达信息”。

- **单总线**：主控请求与传感器返回的数据共用 DATA，交替控制线路。
- **时序**：规定谁先拉低、保持多久、何时释放，以及接收方何时检测电平。
- **数据位**：每位都包含低电平和高电平，靠高电平的长短区分 0、1；不是高电平本身就代表 1。

这属于器件规定的单线通信协议，可通过 GPIO 与计时逻辑实现；它不是 I2C，也不能当作 Dallas／Maxim 的 1-Wire 协议。DHT11 的一帧也没有可用来寻址不同传感器的设备地址，因此通常为每个 DHT11 分配独立数据引脚，不能像有地址的 I2C 器件一样直接并接并分别读取。

#### 3.2.2 接线和“释放总线”

```text
兼容的供电／逻辑电源 ── 上拉电阻（手册典型 4.7 kΩ）──┐
                                                  │
ATmega328PB 的一个 GPIO ────────────────────────── DATA ── DHT11
ATmega328PB GND ────────────────────────────────── GND ─── DHT11
```

DHT11 另接 VCC。裸器件与三针模块的引脚顺序可能不同，模块可能已带上拉，实际接线按实物确认。手册要求数据口采用开漏或三态方式：需要低电平时主动拉低，需要高电平时停止驱动，让上拉电阻把线路拉高，避免主控强推高电平而传感器同时拉低。

在 AVR 上可以通过“输出低／输入高阻”切换模拟这种行为。以下假设接 PD2，仅示意寄存器用法，实际引脚待核对，并假设已配合适的外部上拉：

```c
// 主控拉低：输出锁存先置 0，再把该位配置为输出。
PORTD &= ~(1U << PD2);
DDRD  |=  (1U << PD2);

// 主控释放：改成输入，外部上拉使总线恢复高电平。
// PORTD 对应位保持 0，不依赖内部弱上拉。
DDRD  &= ~(1U << PD2);

// 读取线路实际电平，读 PIN 寄存器。
bool data_is_high = (PIND & (1U << PD2)) != 0;
```

**释放不等于主控一直输出高电平。** “切成输入”是把控制权让给传感器，主控仍然可以读取 DATA 电平。AVR 寄存器行为见 [Microchip 数字 I/O 说明](https://developerhelp.microchip.com/xwiki/bin/view/products/mcu-mpu/8-bit-avr/structure/ioports/)。

#### 3.2.3 一次读取怎样进行？

| 阶段 | 谁控制 DATA | 按所引手册的时序 | 主控做什么 |
| --- | --- | --- | --- |
| 上电／空闲 | 双方释放，由上拉保持高 | 上电后至少等待 2 s。 | 初始化引脚和计时，暂不发起读取。 |
| 起始请求 | 主控 | 拉低 18～30 ms，典型 20 ms。 | GPIO 输出低，通知 DHT11 准备通信。 |
| 交接 | 主控释放 | 到传感器响应前约 10～35 μs。 | 改成输入，及时检测响应，不能长时间延时后才来观察。 |
| 应答 | DHT11 | 先低 78～88 μs（典型 83），再高 80～92 μs（典型 87）。 | 检查低、高及随后下降沿是否在限时内出现。 |
| 40 个数据位 | DHT11 | 每位先低 50～58 μs；随后用高电平长度表示 0／1。 | 逐位测量并组装 5 字节。 |
| 结束 | DHT11 后释放 | 最后一位后再低约 54 μs，随后线路回高。 | 完成校验、解析，维持释放状态。 |

```text
空闲高 → 主控拉低约 20 ms → 主控释放
 → DHT11 应答：低约 83 μs、高约 87 μs
 → 湿度字节 × 2 → 温度字节 × 2 → 校验字节
 → DHT11 结束并释放 → 主控检查结果
```

起始低电平是毫秒级，接收数据是微秒级，不能把两个单位混淆。读取的是数字结果，温湿度的物理测量和内部转换由 DHT11 完成，AVR 不需要再用自己的 ADC 测量 DATA。

#### 3.2.4 没有时钟线，怎么区分 0 和 1？

两种数据位的低电平前导相近，区别在后面的高电平：

```text
数据 0：低约 54 μs + 高 23～27 μs
数据 1：低约 54 μs + 高 68～74 μs
```

主控发现上升沿后开始计时，发现下降沿时结束计时，即得到高电平宽度。可在两个区间之间选判决门限，例如约 50 μs，短于门限解释为 0，长于门限解释为 1；这个门限是实现选择，不是传感器规定的额外命令。实际应结合计时误差及有效脉宽范围，拒绝明显异常的波形。

计时可用 GPIO 轮询配合硬件定时器；也可按可用引脚、外设设计边沿中断／输入捕获。另一种常见思路是上升沿后约 40 μs 采样，短高脉冲此时已结束而长高脉冲仍为高，但同样要求延时准确、状态同步正确。当前未确认项目使用哪一种。

**数据高位先发。** 逐位接收时，先把当前字节左移一位，再并入这次读到的位：

```c
bytes[i / 8] = (uint8_t)((bytes[i / 8] << 1) | bit);
```

这行只是把串行位流拼成字节，不会主动接收电平；`bit` 必须先由脉宽判断得到，`bytes` 初始应清零。

#### 3.2.5 40 位数据怎样变成温湿度？

| 字节 | 含义 |
| --- | --- |
| `bytes[0]` | 湿度整数部分。 |
| `bytes[1]` | 湿度小数部分，解释按实际版本。 |
| `bytes[2]` | 温度整数部分。 |
| `bytes[3]` | 温度小数／符号信息，解释按实际版本。 |
| `bytes[4]` | 前 4 字节累加结果的低 8 位。 |

教学例子：收到十进制 `[60, 0, 25, 0, 85]`，前四字节和为 85，校验一致，整数部分表示湿度 60 %RH、温度 25 ℃。这只是说明数据格式，不是项目实测记录。

```c
uint8_t checksum = (uint8_t)(bytes[0] + bytes[1]
                         + bytes[2] + bytes[3]);

if (checksum != bytes[4]) {
    return DHT_CHECKSUM_ERROR;  // 示例错误码
}

// 本例两个小数字节为 0，以下只展示整数部分。
uint8_t humidity_integer = bytes[0];
uint8_t temperature_integer = bytes[2];
```

这是 **8 位累加校验和，不是 CRC**，也不能发现所有可能的数据错误。简历中的 CRC 需要另核对 SGP30 响应校验或 UART 协议，不能说 DHT11 的最后一个字节采用 CRC。

旧版常见资料将 DHT11 小数字节写为保留或读出为零；本次引用的 2022 年版支持小数，温度低字节 Bit7 还表示符号。不能把 DHT22 的 16 位数值除以 10 的解析方式直接套过来。由于项目实物版本未确认，本笔记不写死通用于所有版本的完整温湿度换算函数。

#### 3.2.6 驱动函数应该怎样组织？

下面为 C 风格流程示例，`wait_level()`、`timer_us()`、延时函数与错误码需由项目实现，不是已找回的原始驱动。各个等待都必须有超时；计时器读取、回绕与精度也要处理。

```c
// bytes[5] 已清零；此前已等足上电时间和两次读取间隔。
dht_drive_low();
delay_ms(20);
dht_release();

// 检测应答低、应答高，再等到第一个数据位的低电平。
if (!wait_level(0, RESPONSE_TIMEOUT_US)) return DHT_TIMEOUT;
if (!wait_level(1, RESPONSE_TIMEOUT_US)) return DHT_TIMEOUT;
if (!wait_level(0, RESPONSE_TIMEOUT_US)) return DHT_TIMEOUT;

for (unsigned i = 0; i < 40; ++i) {
    if (!wait_level(1, BIT_TIMEOUT_US)) return DHT_TIMEOUT;
    uint16_t start = timer_us();

    if (!wait_level(0, BIT_TIMEOUT_US)) return DHT_TIMEOUT;
    uint16_t width = (uint16_t)(timer_us() - start);

    // 实际驱动还应检查 width 是否落在合理脉宽范围。
    uint8_t bit = (width > 50U) ? 1U : 0U;
    bytes[i / 8] = (uint8_t)((bytes[i / 8] << 1) | bit);
}

// 然后检查结束／释放状态、累加校验和，再更新有效样本。
```

`wait_level(level, timeout)` 表示“在限时内等到目标电平”；参数以真实微秒计时，不把空循环次数直接当作时间。若驱动修改了中断状态，所有成功和失败出口都应恢复原状态；示例省略了这些平台相关细节。

#### 3.2.7 这个项目尤其要注意的时序与异常

- **接收超时：** 传感器断线、引脚接错或线路卡住时，不允许 `while (DATA == ...)` 无限等待；应返回无响应、接收超时、校验失败等状态。失败后保留上一份有效数值时，应同时标注时间与过期状态。
- **中断干扰：** 数十微秒的高脉宽可能被耗时中断打断，导致错误判位。不是一律全程关中断；若软件接收确实需要屏蔽，应限制在必要窗口，起始的约 20 ms 低电平不必因此全部屏蔽，并评估接收窗口内数毫秒屏蔽对 UART、定时节拍的影响。可以再考虑捕获／边沿计时方案，而不是让其他模块承担丢数据风险。
- **延时精度：** 若使用 AVR 忙等延时，编译的 `F_CPU`、实际系统时钟和优化设置必须匹配；定时器方案要确认分频和计数单位，不能仅凭函数叫 `delay_us()` 就认为准确。
- **电气与诊断：** 先确认电源、共地、上拉和引脚输入模式，再用示波器／逻辑分析仪看“起始 → 应答 → 40 位 → 结束”。无应答与有波形但校验失败是不同定位方向。
- **1 Hz 与器件周期分开：** 所引手册规定上电后至少等待 2 s，两次通信至少间隔 2 s；并说明读出的是此前采集的结果，通信结束后再进行下一次采集。可将 SGP30／系统处理安排为 1 Hz、DHT11 至少每 2 s 读取一次，中间显示最近有效值和时间戳。这是建议方案，项目当时是否已分别调度仍待源码确认；不能把“通信完成很快”当成“可以每秒获取一份新的温湿度”。

**面试可回答：** “DHT11 由一个 GPIO 按器件的单线时序读取。主控先拉低约 20 ms，再释放线路，确认传感器应答，然后根据 40 个数据位的高电平宽度判断 0、1，高位先收并拼成 5 字节。前四字节是温湿度，最后一字节是累加校验和。驱动还要处理超时、微秒计时及中断影响，读取周期按实际器件手册安排。我会结合原始驱动再确认当时具体采用的计时方法。”

### 3.3 数据有效性与报警

建议解释为“每个样本有数值、单位、采样时刻和有效性”，但结构与实现待代码确认。异常值过滤、连续阈值判断不是一回事：前者处理测量异常，后者防止单次波动频繁报警。若每秒一次且要求连续 N 个有效样本超限，检测延迟与 N 有关；缺测是否清零计数、退出报警是否有回差，应按实际逻辑说明。

记录过期值与当前值需要区分；传感器断线不应无限显示最后一条读数却不标记异常。

## 4. LCD、报警与 SPI 共享

ST7735 需要按照实际屏幕模块初始化、设置绘图窗口，再发送像素数据。颜色格式、方向、分辨率和 SPI 模式要看模块与代码，不根据 ST7735 名字猜具体配置。

ATmega328PB 只有 2 KB SRAM，不能默认保存整屏 framebuffer；要说明是否用局部字符／区域绘制、逐块输出或其他方法。这个内存约束也影响 SD 缓冲、UART 帧、库函数栈和动态分配。

若 LCD 与 SD 共用 SPI，通常需要独立 CS，并在选设备前配置相应模式和频率；未选设备不能错误驱动共享线路。是否共用同一 SPI 控制器是待核实项。

声光报警的输出引脚、电流驱动和持续时间应由实际电路确认；如使用较耗时蜂鸣流程，要避免阻塞周期采样。

## 5. 自定义 UART 与 ESP32 上传

简历确认设计过 UART 数据帧，但没有给出字段。不能现在写死帧头、固定字节数或 CRC 多项式。后续应补一条真实十六进制消息，逐字节解释：

| 必须确认的内容 | 为什么影响可靠性 |
| --- | --- |
| 帧边界、长度与版本 | 接收可以分多次到达，也可能粘在一起；必须有长度上限。 |
| 数值单位、缩放与字节序 | 两个 MCU 不能只靠结构体内存布局互相猜。 |
| 校验范围与算法 | 只写“CRC16”不足以保证两端一致。 |
| 采样序号／时间／有效状态 | 区分丢包、旧数据、重复与测量失败；是否已有待确认。 |
| 超时、截断与重新同步 | 一个坏包不能让解析器永久错位。 |
| 发送／接收方式 | 轮询还是中断、缓冲多大、满时怎么办，按实际工程回答。 |

ESP32 的 Arduino 框架只是开发环境，不能据此推断具体云平台或上传协议。要补 Wi-Fi 连接、云端目标、认证、上传周期、断线重连，以及上传失败是否影响 AVR 主控采样。

“持续运行验证稳定”应补持续时长、样本数量、丢包／校验失败统计与网络条件。没有记录时，不补造“零丢包”或提升比例。

## 6. SD 卡 Bootloader 更新

### 6.1 必须与 STM32 启动方式区分

ATmega328PB 是 AVR，不能套用 Cortex-M 的初始 MSP、VTOR 和 Reset_Handler 跳转流程。器件提供 Boot Loader Section、自编程 SPM、相关熔丝和锁定位；实际 Bootloader 链接位置、大小、复位入口和保护配置需要核对。

在这个方案中，SPI 用于从 SD 卡读文件；向 MCU 内部 Flash 写入则使用器件自编程机制，不是“经 SPI 直接写内部 Flash”。

### 6.2 简化更新流程及实现边界

```text
复位 → Bootloader 判断更新条件
 → 找到并检查镜像 → 分块读取
 → 按应用 Flash 页擦除／编程 → 读回或校验
 → 记录更新结果 → 按 AVR 要求启动应用
```

以上是需要与源码逐步对上的说明，不代表所有校验与提交步骤都已实现。重点追问：SD 使用文件系统还是固定扇区？库占多少 Flash/RAM？镜像怎样限制到应用区？最后不足一页如何处理？缺卡、读失败和中途断电后怎样恢复？

若只有一份应用镜像，写到一半可能破坏旧应用；只要 Bootloader 保持有效，也许能重新更新，但不能直接声称具备自动回滚。CRC 检测意外损坏，也不能代替固件签名验证。
