## 2. 目标与端到端链路

```text
语音输入 → 音频采样／缓冲 → MQTT 上传
 → Azure 上的 Python ASR 服务 → 识别结果／控制命令下发
 → MCU 命令校验与分发 → 舵机动作、OLED 状态等反馈

旁路：IMU 采集、网络状态管理、电源管理、OTA 更新。
```

这是端云协同：MCU 负责采集、通信与本地执行，云端负责简历所述语音识别。不能把它表述为 MCU 上运行了完整 ASR 模型。闭环也要说明是“语音请求到动作反馈的业务闭环”，不能据此认定每个舵机关节都有位置反馈控制。

### 2.1 SiWG917 主控选型

选型的核心理由是：SiWG917 将应用处理与无线连接集成在同一平台，匹配本项目“端侧采集与控制、云端语音识别”的需求。以下从需求适配解释选择，不虚构与其他方案的成本、功耗或性能实测结果。

| 资源 | 官方能力与本人确认的项目配置 | 对机器狗的价值 |
| --- | --- | --- |
| 应用处理器 | Cortex-M4，最高 180 MHz；本人确认项目主频 180 MHz。 | 运行 FreeRTOS，组织音频数据、命令解析、动作和外围设备业务。 |
| 网络处理器 | 独立 NWP，最高 160 MHz，运行厂商无线及相关网络固件。 | 分担无线连接和网络协议处理，使应用开发集中于产品功能。 |
| 无线连接 | 集成 Wi-Fi，并支持 BLE。 | Wi-Fi 支撑音频上传、结果下发和联网升级；未确认项目使用 BLE，不把它列为已实现功能。 |
| 非易失存储 | 所用 SiWG917Y121MGABA 模块配置 8 MB Flash。 | 为固件、资源、配置和升级布局提供容量，但不能直接视为应用独享空间。 |
| 应用运行内存 | 本人确认 M4 分配 192 KB SRAM。 | 保存线程栈、SDK 运行数据、音频和消息缓冲，容量需要按峰值预算。 |
| 外设接口 | 包含 I2S、I2C、PWM／定时器、UART、SPI 等。 | 覆盖音频采集／播放、OLED、IMU、舵机和调试等连接需求，具体实例与复用按板级配置确认。 |

参数依据：[SiWG917Y 官方数据手册](https://www.silabs.com/documents/public/data-sheets/siwg917y-datasheet.pdf)、[所用模块系列的容量配置](https://www.silabs.com/wireless/wi-fi/siwx917y-wireless-modules/device.siwg917y121mga)。180 MHz、160 MHz 分别属于应用和网络处理子系统，不能相加成一个 CPU 的主频。

#### 2.1.1 M4 与 NWP 为什么适合本项目？

可以把两个子系统理解为分工不同的工作人员：M4 处理“采集什么、上传哪段录音、收到命令后做什么动作”，NWP 处理厂商实现的无线及相关网络工作。它们通过平台 SDK 协作，通常不需要应用自行实现 Wi-Fi 底层协议。

```text
M4 应用侧（FreeRTOS 业务任务）
  音频采集／播放、录音管理、MQTT 业务组织
  命令处理、舵机、OLED、按键、OTA 状态
               ↕ SDK 调用与数据／事件交接
NWP 网络侧（厂商固件）
  无线连接及相关网络协议处理
               ↕ Wi-Fi
路由器与云端服务
```

这不是两个可以随意分配应用线程的对等核心：本项目的 9 个 FreeRTOS 应用任务运行在 M4 侧，不把某条业务任务直接算成在 NWP 运行。MQTT 等功能究竟由哪一侧处理哪些环节，取决于 SDK 和接口方式；M4 仍需管理消息、回调、数据交接和重连等业务。

NWP 分担工作也不意味着应用调用永远不阻塞。若 M4 的任务同步等待网络结果，仍可能拖延其他工作；因此还需要合理的任务分工、有界缓冲和等待机制。

#### 2.1.2 180 MHz 与外设资源提供什么？

本项目把复杂语音识别交给云端，MCU 主要负责采集、数据整理、通信组织和本地执行。180 MHz M4 为这些计算提供处理余量，外设则承担对应接口工作；最终是否满足实时要求，还要看音频丢块／播放欠载、CPU 占用及最坏动作响应，不能只看主频。

I2S 连接数字音频设备，I2C 可连接 OLED 和 IMU，PWM／定时器用于舵机控制信号，UART／SPI 可用于调试或扩展。芯片具备这些资源，不代表任意引脚组合都能同时使用，也不表示项目已启用每个接口实例。

#### 2.1.3 8 MB Flash 与 192 KB SRAM 怎样解释？

Flash 主要保存固件和其他非易失内容；SRAM 是任务运行时的工作空间，二者不能互相替代。8 MB Flash 能为软件及升级布局提供余量，但具体还要扣除平台固件、分区和资源占用；不能仅凭容量宣称已实现双镜像、回滚或掉电安全升级。

官方说明总 SRAM 为 672 KB，可在 M4 与 NWP 间按支持的方案分配。192 KB M4 应用侧对应一种 480 KB NWP／192 KB M4 的配置，因此本人所说的 192 KB 是应用侧容量，不是全芯片只有 192 KB。参考 [官方 SRAM 分配说明](https://docs.silabs.com/wifi-application-notes/latest/wifi-siwx917-soc-memory-map/static-random-access-memory-sram)。

应用侧还需为任务栈、内核／SDK、通信和音频缓冲分配空间。当前确认的流程是等待完整录音后上传，必须明确最长录音与存放位置；容量计算示例见第 4 节。模块可能具备的其他存储资源，未确认启用前不计入可用录音预算。

与读卡器的 H563 选型侧重点不同：读卡器强调 USB、Type-C／PD 和卡片外围集成，本项目强调无线连接、音频接口及本地执行。不能因为 H563 主频更高，就认为它天然更适合联网语音机器狗；替代方案还需比较外接无线器件、软件集成和实际资源需求。

## 3. 应用任务、优先级与 FreeRTOS 重构

<a id="task-priorities"></a>

### 3.1 本人确认的 9 个应用任务

这里记录的是本人创建的应用任务，不把 FreeRTOS Idle、可选的软件定时器服务任务或 SDK 可能创建的内部任务计入这 9 个。任务名与职责来自本轮确认，最后一列是建议的运行方式，不代表已核验原函数。

| 任务名 | 当前优先级 | 已确认职责 | 合理的等待／执行方式，待核对 |
| --- | --- | --- | --- |
| `app` | Low | Wi-Fi 初始化、OTA 状态管理。 | 初始化后等状态事件或有节奏地处理状态机；不要空转查询。 |
| `mqtt` | BelowNormal | MQTT 连接、订阅和发布。 | 等待网络事件或待发消息，兼顾 SDK 要求的连接维护及重连。 |
| `i2s_capture` | AboveNormal | 处理录音接收块。 | 等待音频块就绪；短时间完成交接和处理，再等待下一块。 |
| `speaker_playback` | AboveNormal | 准备并发送播放块。 | 等待播放请求、可写缓冲或发送完成事件；无播放时阻塞。 |
| `pwm_control` | Normal | 舵机动作控制。 | 等待动作命令，或按确定周期推进动作计划，避免忙等整个动作。 |
| `i2c_leader` | BelowNormal | OLED 刷新。 | 等待显示变化或按显示周期刷新，限制每轮工作量。 |
| `button0` | BelowNormal | 按键扫描。 | 周期扫描并消抖，扫描后进入阻塞延时；具体周期未确认。 |
| `led_blink` | BelowNormal | LED 灯光闪烁。 | 更新灯状态后延时等待，不循环空转等时间。 |
| `audio_uploader` | Low | 等待完整录音并上传。 | 等待录音完成，管理有效长度与缓冲所有权，再提交上传工作。 |

相对等级从高到低为：

```text
AboveNormal：i2s_capture、speaker_playback
      ↓
Normal：pwm_control
      ↓
BelowNormal：mqtt、i2c_leader、button0、led_blink
      ↓
Low：app、audio_uploader
```

Low／BelowNormal／Normal／AboveNormal 这类名称常见于 CMSIS-RTOS 封装；当前保留本人提供的相对等级，不断言工程采用了哪一版 CMSIS，也不把它们直接转换成原生 FreeRTOS 数值。具体映射要看创建接口、适配层和 `configMAX_PRIORITIES`。参考 [Arm CMSIS-RTOS2 优先级说明](https://arm-software.github.io/CMSIS_6/main/RTOS2/group__CMSIS__RTOS__ThreadMgmt.html)。

这些应用任务运行在 M4 应用侧；NWP 的存在不表示能把某个 FreeRTOS 业务任务直接搬到 NWP，也不表示网络 SDK 调用不会等待。

### 3.2 功能模块与任务边界

下面是职责分层，不能再把每一行当作额外创建的线程。命令分发、IMU、会话管理等功能目前尚未明确归属哪个任务，不补造第 10 个任务；OTA 已明确由 `app` 管理状态。

| 模块 | 职责与输入输出 | 关键边界 |
| --- | --- | --- |
| 音频采集 | 从接口取得 PCM 数据块，发布可用缓冲。 | ISR／回调尽量只交接，不做网络上传。 |
| 音频播放 | 按播放需求准备数据块并提交发送。 | 对应 `speaker_playback`；音源和是否允许边录边播未确认。 |
| 音频与识别会话 | 管理开始／结束、分块及请求编号。 | 迟到结果不能错误驱动下一次会话。 |
| MQTT／网络 | 连接、订阅、发布、重连和错误状态。 | 避免多个任务无约束并发调用同一客户端。 |
| 命令分发 | 校验命令，转换为受支持动作。 | 云端字符串不直接变成任意执行入口。 |
| 舵机控制 | 按动作计划更新 PWM 和安全状态。 | 网络超时不应使控制任务永久阻塞。 |
| OLED／状态显示 | 显示系统状态与结果。 | 一般可合并过时画面，只显示最新状态。 |
| IMU | 输出有单位、时间戳与有效性的测量。 | 数据用途及与动作控制关系待确认。 |
| OTA | 升级状态、下载和交接启动。 | 更新时哪些业务必须安全暂停。 |

重构时要能举出 Superloop 中的一条阻塞链，例如网络等待拖延了其他轮询；这只是排查方向，真实案例需从旧代码和日志确认。多任务不自动提升实时性：还要确保任务及时阻塞、锁占用有界、缓冲足够、优先级合理。

已有 9 个任务的名称、优先级和职责；后续可补栈大小、周期／触发方式、阻塞点、共享资源及测量结果，不猜测数值。

### 3.3 通信与资源选择

- 命令／状态记录需要保留顺序时用队列；只通知确定任务“音频块完成”可用任务通知或信号量。
- I2C 共享总线按完整事务互斥；显示与 IMU 是否共用同一控制器，要核对实际接线。
- 大块音频可交接缓冲区指针，但应定义生产、消费、归还和队列满策略；队列复制指针并不复制音频内容。
- 事件组适合网络就绪、采集结束等条件组合，不适合累计每个音频块。
- 队列满意味着处理能力或突发预算不足。音频、动作命令和显示状态的丢弃策略应分别定义。

`audio_uploader` 与 `mqtt` 的边界尤其需要说清：前者负责“哪段录音、有效长度、何时上传”，后者负责连接、订阅及实际消息发布。可以设计为上传任务把待发数据描述交给 MQTT 任务，由一个任务统一操作客户端；这是推荐分工，不是当前已核实实现。若两者实际都会直接调用同一个 MQTT 客户端，应按 SDK 的线程安全约定处理，不能默认并发调用安全。

<a id="priority-review"></a>

### 3.4 当前优先级配置的分析与优化空间

总体方向合理：连续音频块可能有明确处理期限，舵机动作需要稳定推进，网络和界面工作放在后面。但仅凭任务名和优先级，不能断定已经发生了调度问题；以下是待验证的优化方向。

#### 3.4.1 高优先级音频任务应短时处理、及时阻塞

两个音频任务都为 AboveNormal 可以成立，不必为了区分它们而强行设成不同级别。关键是处理完当前数据块就等待下一次事件；如果一直轮询、做长时间计算或反复处理过时积压，Normal 及以下任务可能长期得不到 CPU。

同级任务是否按 tick 轮转取决于调度配置；即使启用时间片，轮转也只在相同最高就绪优先级之间发生，不能据此保证低优先级任务得到 CPU。需要关注 `configUSE_PREEMPTION`、`configUSE_TIME_SLICING` 及实际封装行为。

音频优先级最终应结合数据块周期、处理耗时、录音溢出和播放欠载来判断。若支持同时录放，还要测二者同时运行的余量；若业务互斥，无须凭空承诺全双工能力。先减少拷贝、控制每轮工作量、合理使用驱动缓冲，再考虑改变优先级。

#### 3.4.2 OLED、按键和 LED 与 MQTT 同级，有拆分空间

目前 `mqtt`、`i2c_leader`、`button0`、`led_blink` 都在 BelowNormal。同级不是天然错误：若每个任务都及时阻塞、工作短小，通常可以合作运行。但网络连接维护与发布，和可延后的显示／灯光刷新，其响应需求不完全相同。

优先考虑让 OLED 只在内容变化时或受控周期刷新，采用有界的分块工作；按键周期扫描并消抖；LED 阻塞延时。注意一次 I2C 事务耗时长，不等于 CPU 一定被占满，要区分驱动忙等和阻塞等待。

若测到 MQTT 被这些工作明显拖延，可考虑把 OLED、普通 LED 闪烁降到 Low，保留 MQTT 在 BelowNormal；按键若承担及时停止录音等交互，可保留相对较高等级。降到 Low 的显示任务也应每轮完成后阻塞，否则仍可能拖延同级上传。这里不直接把“MQTT 提到最高”作为通用答案。

#### 3.4.3 舵机任务的周期与实现比单纯提级更重要

`pwm_control` 为 Normal，高于界面和网络、低于音频，是合理起点。若 PWM 由硬件外设持续输出，任务通常负责更新目标脉宽和动作进度，不必持续占 CPU 生成每个脉冲；若实际采用软件波形，则需另行评估，不能直接套用这个结论。

优先使用事件或稳定周期推进动作，避免网络等待拖住控制；测试音频负载下的最坏动作更新间隔。周期任务可参考 FreeRTOS 的 `xTaskDelayUntil()` 或所用适配层的周期等待方式，具体 tick 换算和周期仍待确认。只有动作期限实际不能满足时，才考虑调整相对优先级或拆分工作。

#### 3.4.4 上传任务为 Low：吞吐、内存和端到端延迟需要一起考虑

本人确认 `audio_uploader` 等完整录音后上传，而非已经实现边录边传。Low 可以避免上传的数据处理抢占音频和动作，但若较高等级任务持续就绪，上传开始和完成可能被拖延，完整录音缓冲也会占用更久。

应先确认上传任务是在做 CPU 密集的数据整理、等待网络，还是仅提交给 MQTT。若主要阻塞等网络，提高任务优先级不能直接提高 Wi-Fi／云端速度；若确实长期拿不到 CPU，可在降低界面负载后，再评估提高到 BelowNormal 的必要性。

同时定义录音缓冲何时转交、何时释放，以及上传中再次录音怎么办。录音完成事件不等于缓冲可以立即复用；消息队列里放指针也不等于复制了录音。192 KB 应用 SRAM 下，完整录音容量与并发会话数量必须有上限。

#### 3.4.5 app 的低优先级与启动／OTA 依赖

Wi-Fi 初始化不必因为“重要”就设最高优先级。若它在其他任务阻塞等待就绪条件时执行，Low 也能完成；但其他任务不能在依赖未准备好时就访问资源，也不能高优先级忙等就绪标志而让初始化任务失去 CPU。

可用明确的网络就绪／失败事件协调启动。`app` 管理 OTA 状态，不代表它应该在运行时无休止查询，也不代表可在任何动作或录音过程中直接擦写、重启；升级需要协调业务状态，按实际流程决定何时暂停、提交和恢复。不能单靠提高 `app` 优先级解决 OTA 协作问题。

#### 3.4.6 共享资源阻塞不能只靠排优先级解决

如果音频或控制路径等待低优先级任务持有的共享锁，可能出现优先级反转。需要缩短持锁范围、按接口约定使用带继承机制的互斥锁，避免持锁等待漫长网络响应。不能只因为数据交接用了队列，就认为所有优先级依赖都会自动得到继承。

**建议的优化顺序：** 先确保空闲时阻塞与每轮工作有界 → 控制 OLED／LED 等非关键工作 → 明确上传与 MQTT 的客户端所有权 → 测量音频、控制、网络的最坏响应 → 根据结果小幅调整等级。当前任务表保留原配置，未把这些建议记为已实施。

机制依据：[FreeRTOS 调度说明](https://github.freertos.org/Documentation/02-Kernel/02-Kernel-features/01-Tasks-and-co-routines/04-Task-scheduling)、[官方调度配置模板](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/main/examples/template_configuration/FreeRTOSConfig.h)、[周期等待接口](https://github.com/FreeRTOS/FreeRTOS-Website-Content/blob/main/content/en-us/Documentation/02-Kernel/04-API-references/02-Task-control/03-xTaskDelayUntil.md)、[FreeRTOS 互斥锁说明](https://freertos.org/Real-time-embedded-RTOS-mutexes.html)。

### 3.5 验证时应观察什么？

- 音频接收块丢失／溢出、播放缓冲欠载、音频块最大处理耗时。
- 舵机动作任务的最大更新间隔，按键触发到业务响应的延迟。
- MQTT 服务／发布的延迟、重连行为、待发队列峰值及满队列处理。
- 完整录音大小、上传耗时、缓冲释放时机及下一次录音的接纳策略。
- 各任务 CPU 占用、最长就绪等待、栈高水位和最低剩余内存。

以上是评估方法，没有当前项目实测数值，不能先写“优化后延迟下降多少”。

## 4. I2S／PCM 音频与云端识别

I2S 是接口时序，PCM 是音频样本表示。要说明实际采样率、有效位数、声道数、时隙宽度、主从关系和数据对齐；时隙宽度可能大于有效采样位数。是否使用 DMA、双缓冲或环形缓冲，需看当前驱动。

**计算示例，不是项目参数：** 16 kHz、16 位、单声道 PCM 的纯样本带宽为 `16000 × 2 = 32000 B/s`；一块 100 ms 数据约 3200 B。协议头、编码和传输重试另算。这样能反推缓冲池容量及最大允许网络停顿，而不靠“队列开大一点”猜测。

本人本轮确认：`audio_uploader` 等待完整录音后上传，不能表述为已经实现边录边传或流式 ASR。仍需确认会话编号、数据格式、有效长度、录音完成条件、上传是否进一步分块以及结果状态。

按上述教学参数，10 秒 PCM 约 320 KB，已经超过本人确认的 192 KB 应用 SRAM 总预算，还未计算栈和 SDK 占用。这不代表项目录音就是 10 秒，只说明整段录音方案必须明确实际采样格式、最长录音和存放位置；不能把 8 MB Flash 或未确认启用的外部 RAM 直接当作空闲录音缓冲。

云端部分需要补：Azure 使用的具体服务、Python 程序入口、ASR 是第三方 API 还是本地部署模型、识别结果怎样映射命令、超时及识别失败如何反馈。没有证据不宣称自训模型或端到端延迟指标。

## 5. MQTT 与异常状态

MQTT 是消息发布／订阅机制，不保证应用层每个动作恰好执行一次。需要从实际配置说明 Topic、QoS、客户端会话、保留消息、重连及请求关联。

面试可以讨论但不能假称已实现的改进：

1. 动作命令带编号和有效期，拒绝重复或过期命令，避免重连后执行陈旧动作。
2. 网络断开时采集缓冲有容量上限，按业务选择丢弃、终止本次会话或重试。
3. 重连成功后恢复订阅，明确是否重新提交未完成请求。
4. 将云端请求耗时与舵机更新分离，防止网络阻塞影响本地动作安全。

实际传输是否使用 TLS、凭据如何配置、断线状态机如何实现，待代码确认。没有这部分实现时如实说明边界。

## 6. 舵机、显示与 IMU

- **SG90／PWM：** 控制输入关注周期和脉宽，角度对应关系需按器件和机械安装标定。没有反馈时，指令角度不是测得的真实角度；运动速度、限位和安全上电状态要另设计。
- **OLED／I2C：** 区分 framebuffer 绘图、命令／数据封装和底层总线。分块刷新可以降低一次占用，但不自动等于 SDK 发送是非阻塞的。
- **IMU：** 补充型号、总线、采样率、坐标系、校准和具体用途。读取姿态不等于已经形成姿态反馈控制。
- **驱动贡献：** 按“控制器 HAL → 器件协议 → 状态与应用集成”说明本人写了哪一层，借鉴的示例与库也明确列出。

已有背景知识可参考 [I2C](../../README.md#i2c)、[OLED 驱动分层与分步刷新](../../README.md#driver-experience)；PWM 参数另按本项目器件与标定记录补充。

## 7. OTA 与固件生命周期

简历确认集成 OTA，但没有提供实际镜像布局与 Bootloader 配置。Silicon Labs 平台的更新要区分应用处理器镜像、网络处理器固件等对象，并核对所用 SDK 版本，不能直接套一张通用 A/B 分区图。

```text
触发升级 → 获取镜像信息 → 下载到指定位置 → 完整性及必要的真实性检查
 → 让业务进入安全状态 → 按平台机制切换／重启 → 检查新版本
```

上面是待映射到实际实现的流程。需要回答：更新入口、镜像地址、长度限制、版本判断、CRC／签名、掉电后行为，以及失败时是否有独立恢复入口。“OTA 已集成”不自动等于双分区、签名验证、试启动确认或回滚都已实现。

如果只调用了 SDK OTA 接口，也可以解释自己做的下载触发、状态衔接和测试；不把平台 Bootloader 说成本人从零实现。

## 8. 硬件与 bring-up

简历包含 3.3 V Buck、5 V Boost、电池管理、多电压域和四层 PCB。准备按电源树解释：输入来源、各路负载、峰值电流、转换损耗、保护和上电顺序。舵机动作及 Wi-Fi 发射时可能产生负载突变，应以波形定位是否影响 MCU；这是假设风险，不是已确认故障。

bring-up 可以按“电源与短路检查 → 复位／时钟／下载 → 调试输出 → 单个外设 → 网络 → 并发整机”解释，并补实际执行记录。四层板要能说明真实层叠、参考地、回流路径和电源／射频／音频布局，不能只说层数多就更稳定。
